# アーキテクチャ：2 本のパイプライン、1 つの LLM、3 つのプロセス

[English](architecture.md) · [中文](architecture.zh.md) · [**日本語**](architecture.ja.md)

```
                               ┌───────────────────────────────────────────────────────┐
   HDMI キャプチャ ─ UVC ─────→│  vision.py（常駐フレーム取得 / OCR / TensorRT rec）   │──→ /api/look
                               └───────────────────────────────────────────────────────┘    │
                                                                                            │
   ┌──────────── voice-bench :8095（音声アシスタント）─────────────────────────────────┐
   │  H340 マイク → KWS「小八你好」→ pw-record → Silero VAD → SenseVoice (ja)          │    │
   │       → LLM(35B) → 文単位に分割 → Piper(ja/zh) → pw-play → ヘッドセット           │←────┘
   │  ブラウザは起動と表示のみ。録音と再生は Jetson 側で実行                           │
   └───────────────────────────────────────────────────────────────────────────────────┘
                                     │ 共有の OpenAI 互換エンドポイント
                          ┌──────────┴──────────┐
                          │  Magnitude :10100   │  （または vLLM :8000）
                          │  Qwen3.5-35B-A3B    │
                          └──────────┬──────────┘
   ┌──────────── caption-bench :8096（会議字幕）───────────────────────────────────────┐
   │  キャプチャ音声 → pw-record（排他なし）→ Segmenter（段階的ポーズ + soft-cut）     │
   │     → SenseVoice → translate_stream（ストリーミング、必要時のみ画面語ヒント）     │
   │     → SSE /api/events → ブラウザが増分 DOM 描画（最新行が最上部）                 │
   └───────────────────────────────────────────────────────────────────────────────────┘
```

**なぜ 2 プロセスに分けるのか**：音声アシスタントは「一問一答で、しかも読み上げる」もの、
字幕は「途切れず流れ続け、リアルタイムである」ものです。両者はスレッドモデルもレイテンシ
予算もまったく違います。無理に 1 つにまとめると、ASR と LLM を取り合ってしまいます。
両者は `voice_server.py` の `/api/look` を通じて OCR 結果を共有しています——**キャプチャ
カードは排他デバイスで、`/dev/video0` を常時保持しているのは voice-bench だけ**です。
字幕側は画面語が必要なときに voice-bench に問い合わせ、自分ではデバイスを開きません。

## なぜ字幕は「ストリーミング + SSE + 増分 DOM」なのか

1. **ストリーミング LLM**：文全体を訳し終えてから表示すると 0.8〜1.3 秒待つことになります。
   トークン単位の push に変えると 0.26 秒で文字が出始めます
2. **SSE**：サーバーは 50ms ごとに更新を確認し、中間状態が届いた時点で push します。
   ポーリングだと最大 250ms 余分に待ちます。サーバー側は `take_updates()`（「取り出すと同時に
   消える」実装）を使いません。2 つの画面が互いにパッチを奪い合うからです。接続ごとに
   自分で訳文のスナップショットと比較します
3. **増分 DOM**：初期は全量 `innerHTML` + ピクセル単位の `scrollY` 復元でした。長い訳文が
   伸びている最中に再構築されるとアンカーがずれ、同じ y が別の内容を指してしまい、「次の一文が
   来た瞬間に前の行が丸ごと消える」現象になります。現在は 1 行 1 ノードを常駐させ、変化した
   テキストノードだけを書き換えます。`#main{overflow-anchor:none}`

並び順は**最新が最上部**で、古い行は下へ押し出されます。視線のアンカーが下端から上端に
変わるため、下へスクロールして古い行を読むときは `top` の差分で `scrollY` を補正します
（逆順では補正の符号は `+`）。

## スレッド／リアルタイム性

字幕経路では、`q_asr`（ASR 待ちの段）と `q_tr`（翻訳待ちの段）が**唯一信頼できる
リアルタイム性の判定指標**です：

```
q_asr = 0, q_tr = 0, dropped = 0   → 追いついている
q_tr が上がり続ける                → 翻訳が追いついていない。まず --ctx-lines を下げ、次に LLM が VRAM を奪っていないか見る
dropped > 0                        → キューが段を捨て始めた。遅延がリアルタイムを超えており、必ず対処する
```

`--tr-workers 1` は確定値です。worker を増やしても 1 文あたりの遅延は変わらず、VRAM を
食うだけです。`--ctx-lines 1` は毎文変わる上文を削るもので、実測で約 90ms の短縮になります。
