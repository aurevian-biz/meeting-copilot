# The LLM: two routes, three engine details you must know

[**English**](llm-serving.md) · [中文](../zh/llm-serving.md) · [日本語](../ja/llm-serving.md)

Both services (`voice_server.py` / `caption_server.py`) recognise exactly one thing: an
**OpenAI-compatible `/chat/completions` endpoint**. So swapping backends needs no business
code change — only the three flags `--llm-base` / `--llm-model` / `--llm-key`.

## 1. Two routes

| | Magnitude + Qwen3.5-35B-A3B | vLLM + Qwen2.5-7B-AWQ |
|---|---|---|
| Endpoint | `http://127.0.0.1:10100/inference/v1` | `http://127.0.0.1:8000/v1` |
| Model id | `hf:unsloth/Qwen3.5-35B-A3B-GGUF/...Q4_K_XL.gguf` | `qwen` |
| Auth | Bearer (generated by Magnitude itself, see below) | none |
| Weights | 22.9G GGUF | about 5.2G AWQ |
| First token (short utterance) | 300~470ms | **90ms** |
| Long answers (read screen / summarise) | **25~35% faster** | slower |
| JA/ZH mixed script / hallucination | clean | emits 「会議的时间确认 needed。」, `-topic1-`, Spanish words |
| Cold start | about 3 minutes (including 150s of weight loading) | about 40 seconds |

**Conclusion**: this system is "Japanese speech, Chinese announcements/captions", so the
language directive is stricter than in a typical scenario. Since the 35B went in, all 7
known translation failures disappeared; the price is 170~370ms more first-token latency on
short utterances. When memory is tight or you only do short caption lines, the 7B is fine
too — see `scripts/llm-vllm.sh`.

### Why a MoE is actually faster on long answers

35B-A3B is a MoE: only about 3B parameters activate per token, while a dense 7B pushes
every parameter through for every token. The cost sits in **prefill** (it has to read
nearly all experts), the payoff sits in **decode**. Hence: short answers (tens of
characters) → the 7B wins; long answers (hundreds of characters) → the 35B wins by 25~35%.

## 2. Starting it and the flags

### Magnitude

```bash
bash scripts/llm-magnitude.sh                 # generate daemon.json for a dedicated dockerd
sudo bash deploy/install-units.sh             # install magnitude / magnitude-dockerd
sudo systemctl start magnitude                # start container → wait for health → explicitly load the model
```

Magnitude's apiKey is **generated by itself on first start**, not configured by us:

```bash
python3 -c "import json; print(json.load(open('$MC_DATA/magnitude-data/.magnitude/config.json'))['network']['apiKey'])"
```

`deploy/install-units.sh` reads it and writes it straight into
`/etc/meeting-copilot/env` (0640). **Do not commit this key to the repository.**

Why a separate dockerd: Magnitude needs `--runtime nvidia` and wants a dedicated 22.9G
data-root, and a separate daemon means "stopping it does not affect other containers on
the machine". If you don't want this setup, drop `DOCKER_HOST` from
`deploy/magnitude-up.sh`.

### vLLM

```bash
bash scripts/llm-vllm.sh
# then change /etc/meeting-copilot/env to:
#   LLM_BASE=http://127.0.0.1:8000/v1
#   LLM_MODEL=qwen
#   LLM_KEY=
```

### Business-side flags

```bash
--llm-base   http://127.0.0.1:10100/inference/v1
--llm-model  hf:unsloth/Qwen3.5-35B-A3B-GGUF/Qwen3.5-35B-A3B-UD-Q4_K_XL.gguf
--llm-key    <Bearer>
```

## 3. Three engine details you must know

### 3.1 `prompt_n` is not "new tokens minus cached"

The engine's `prompt_n` is **the number of tokens actually processed this round**, and
`cache_n` is the number of reused tokens; only the sum of the two is the whole prompt.
**The new tokens are `prompt_n`**, not `prompt_n - cache_n` (we had this backwards early
on, which made the slope estimate wrong by a factor of two).

The rule of thumb that follows (35B-A3B):

```
TTFT ≈ 65ms + 3.5~6.5ms × new tokens       # measured slope in production: 4.5ms/token
```

A 200ms first token is a hard floor — stop chasing it lower.

### 3.2 Short prompts are actually slower

The intuition is "cut the system down to 70 tokens and prefill gets faster". Measured:
**no**.

- Long prefix (full, about 250 tokens): stably reuses 290 tokens, high `cache_n`
- Short prefix (short, about 70 tokens): when the user content changes on every
  utterance, `cache_n` is **constantly 0** (24/24), the whole thing is re-prefilled, and
  the first token is actually slower
- Send the same prompt twice in a row: both variants hit (`297/1` vs `91/1`) → it is not
  that "a short prompt cannot be cached", it is that **content that changes on every
  utterance invalidates the prefix**

So the default is `--tr-prompt full`. `short` is kept as a control experiment and is not
recommended for production. Likewise `--ctx-lines 1` cutting those 30 tokens of prior
context is a real saving (about −90ms), because that part **changes on every utterance**;
`--tr-workers 1` makes no difference to latency, it just competes less for VRAM.

### 3.3 The language directive goes at the end of user, and must be duplicated in system

The 35B is extremely sensitive to directive position (Japanese meeting → Chinese output):

| Directive position | Chinese-output success rate |
|---|---|
| system tail only | **0/6** |
| user tail only | **6/6** |
| system + user both | 4/4 |

Implemented in `_lang_directive()` in `voice_server.py`: one copy is appended to the end of
the user content, and one is carried in system as well. Same on the captions side — see
`_tr_system()` in `caption_server.py`.

Two more 35B-specific traps:

- Qwen3.5's chat template **enables thinking by default**: `max_tokens=200` burns entirely
  in thinking and `content` is an empty string, which shows up as "no translation". You
  must pass `chat_template_kwargs={"enable_thinking": false}`
- **Dynamic system**: as soon as the word 「[屏幕文字]」 appears in system, the model goes
  off to quote it. So when there is no OCR content, use a different system that never
  mentions 「屏幕文字」 at all

## 4. Don't investigate these as bugs

- vLLM cannot hit the 35B's prefix cache (1056-token granularity); this is a **physical
  property of the model + engine**
- The 35B's prefill is expensive and decode is cheap; dense is the other way round. Don't
  apply 7B intuition to a MoE
- The first `models load` on cold start takes about 150s; a log that does not move is not
  a hang
