# jetson-voice-assistant

Jetson AGX Orin 64GB 上の音声対話チェーン。現在は**実用段階**にあり、収音 → ASR → LLM → TTS が一つの閉ループとしてつながっていて、ブラウザのテストベンチから直接話しかけられます。

## 1.1 TTS インストールの三つの罠（すべて踏んだ）

1. **`piper-phonemize` は aarch64 用の wheel がない**ので入らない —— ただし `piper-tts` 1.8.0 はすでにこれに依存しておらず、直接インストールできる（`piper_tts-1.8.0-cp39-abi3-manylinux_2_28_aarch64.whl`）
2. **日本語には `pyopenjtalk` が必要**だが、公式の `pyopenjtalk` はソースパッケージのみ（OpenJTalk のビルドが必要）。**`pyopenjtalk-plus`** に切り替えた。cp312 aarch64 の wheel があり、モジュール名は依然として `pyopenjtalk` なので drop-in 置換になる
3. **CLI で wav ヘッダを書くと `# channels not specified` で落ちる** —— Python API の `PiperVoice.synthesize_wav()` に切り替えた。`tts_probe.py` 参照

Piper の日本語は**声質が一つだけ**：`ja_JP-hi_fi_captain-medium`（2 話者）。これ以上の音質が欲しければ VOICEVOX に替えるか MeloTTS を直すしかありません。

## 2. 収音：先に処理すべき二つの問題

### 2.1 60Hz の電源ハム（実測）

元のノイズフロアは **−30.6 dBFS**、スペクトルの最強点が 60Hz で 120Hz の高調波があり、0–80Hz がエネルギーの 38.4% を占めていました。これは室内ノイズではなく、電源周波数／グラウンドループです。

150Hz、4 次ハイパスをかけた後：

| | ハイパス前 | ハイパス後 |
|---|---|---|
| ノイズフロア | −30.6 dBFS | **−48.8 ~ −56.6 dBFS** |
| 音声区間の SNR | 9.8 dB | **34 dB** |

音声の主要帯域は 300Hz–3kHz なので、150Hz 以下を切っても ASR には無損失です。**この手順は省けません**。省くと VAD のしきい値がハムに押し上げられ、人の声が切り出せなくなります。

### 2.2 キャプチャゲイン（調整済み、戻せる）

H340 のキャプチャゲインは出荷時がフルスケール `44/44 = +8dB` で、実測で 33 サンプルのクリップがありました。

```bash
amixer -c 0 cset numid=4 32     # 44 → 32、つまり +8dB → 0dB
amixer -c 0 cset numid=4 44     # 元の値に戻す
```

注意：このコントロールには Playback/Capture のプレフィックスが**付いていない**ため、`amixer sget 'Mic Capture Volume'` は見つからずエラーになります。必ず `numid` を使います。

## 3. エンジン比較（同じ日本語、3.29s / 3.56s）

ユーザーが口述した内容（推定）：「このセクションのインターフェース仕様を確認してください」

| エンジン | 区間1 | 区間2 | RTF | 誤りの型 |
|---|---|---|---|---|
| whisper large-v3-turbo | この**セクション**の…**使用**を | この**セクッション**の…**使用**を | 2.2 | 漢字の意味置換 |
| whisper small | このセクションの…**使用**を | この**セキューション**の**インタフェース**を | 0.92 | カタカナ退化 + 語落ち |
| **SenseVoice int8** | この**セシ**の…**仕様**を | この**石晶**の**インタフェース** **仕様**を | **0.04** | カタカナ崩壊 |

二つのエンジンの失敗点は**重なっていません**。whisper はカタカナを正しく読むが `仕様` を `使用` に置き換える（意味レベルの誤りで、後から気づけない）。SenseVoice は `仕様` を正しく読むが `セクション` を `セシ`/`石晶` に崩す（字形レベルの誤りで、文脈から修復できる）。

**結論**：ASR は SenseVoice を使う（50 倍速く、双方向にはこれしか成立しない）。カタカナの誤りはローカル LLM の誤り訂正に任せる。これは `work-memory` の OCR における「決定論的抽出 + LLM 訂正」と同じパラダイムです。

### なぜ whisper を使えないのか

`ctranslate2` の aarch64 wheel は**CPU 専用**です。`get_cuda_device_count() == 0` で、faster-whisper はこのマシンで GPU を使えません。12 スレッドで頭打ち（デフォルトは 4 スレッドのみ、引き上げて RTF 3.83 → 2.08）。GPU は LLM に残さなければなりません。

## 3.1 TTS の実測と閉ループ検証

```
ロード      1.803s
初回チャンク遅延  636.1ms      ← 双方向で実際に体感される遅延。全体 RTF よりずっと重要
合成      1.053s / 音声 7.83s  → RTF 0.135
サンプリングレート    22050Hz   話速 6.6 文字/秒
```

閉ループ検証（合成 → 読み戻し、原文は既知）：

| | テキスト |
|---|---|
| 原文 | この**設計書**のインターフェース仕様を確認してください。データベース接続には**コネクションプール**を使用します。 |
| SenseVoice 読み戻し | この**設計者**のインターフェース仕様を確認してください、データベース接続にはコネクションプールを使用します。 |

誤りは `設計書→設計者`（しょ→しゃ）の一箇所だけで、長いカタカナ語はすべて正解でした。**これは合成音でのスコア**であり、実際のマイク録音よりはるかに簡単なので、実機の精度としては扱えません。

## 4. Web テストベンチ（`voice_server.py`）

ブラウザで **http://127.0.0.1:8095** を開き、一度クリックして話し始めると、サーバーが録音・認識・応答・合成を行い、ブラウザは受け取りながら再生します。

読み上げはデフォルトで**ページを開いたマシン**から音が出ます。Jetson に挿したヘッドセットから鳴らしたい場合は「音声：ヘッドセット」を有効にします（4.11 参照）。

サービスは systemd に登録済みで、再起動すると自動で復旧します：

```bash
sudo systemctl status voice-bench      # 状態
sudo systemctl restart voice-bench     # コード変更後の再起動
journalctl -u voice-bench -f           # ログを見る
```

### 4.1 三つの設計上のトレードオフ

| 決定 | 理由 |
|---|---|
| **録音はサーバー側** | マイクは Jetson に挿さっている。ブラウザ録音ではノート PC のマイクしか使われず、実機の収音を測れない |
| **Silero VAD で終了判定、長さ固定なし** | 固定 N 秒録音では「話し終わっても待たされる」ぶんが実際の遅延を覆い隠す。VAD は 0.6 秒の無音で締める |
| **文単位で合成し、逐文返す** | 全体を一括合成すると LLM の生成完了を待つことになる。ここでは LLM が一文吐くたびに合成してブラウザへ送る |

### 4.2 なぜエネルギー VAD をやめたのか

当初は「ノイズフロア + マージン」の絶対しきい値を使っていましたが、実測で二種類の失敗がどちらも発生しました：

- **ゲインが高いとき**：ノイズフロアが音声で汚染される → しきい値が −20dB まで上がる → 音声自身が無音と判定され、0.81s しか取れない（`thr_db` と `peak_db` が完全に一致するのがこの症状の指紋）
- **環境が騒がしいとき**：ノイズ自体がしきい値を上回る → 「話し終わった」を永遠に判定できない → 毎回 12 秒の上限に張り付く（ユーザーの実測 2 件はいずれも `record_s: 12.04`）

Silero VAD は 512 サンプル窓の音声確率に基づき、ゲインや定常ノイズに敏感ではありません。しかも「話し終わってからどれだけで一段落とみなすか」を内蔵しています。置き換えた後は、7.59 秒の音声が再生終了と同時に締められ、上限に張り付くことはなくなりました。

### 4.3 中国語 / 日本語の声質自動切替

Piper の日本語音声で中国語を読ませても、中国語音声で日本語を読ませても大きく調子が崩れます。判定規則：**仮名があれば → 日本語、仮名がなく漢字があれば → 中国語**（日中混在は存在しないことを確認済みで、文単位の判定で十分）。

さらに「応答をどの言語で返すか」はモデル自身に決めさせません。実測では、直前の数ターンが中国語のときにユーザーが日本語に切り替えても、モデルは文脈のスタイルに引きずられて中国語で答え続けました。そこで毎ターン、その時点の文の言語に応じてハード指示を一つ追加します。言語を固定したい場合は `--reply-lang zh|ja`、デフォルトは `auto`。

#### 実際に起きた二つの障害（修正済み）

**① `合成失敗：# channels not specified`** —— 録音でもサウンドカードの問題でもありません。テキストに発音可能な文字が一つもない場合（`。`、`……`、`「」`、空白のみ）、Piper の音素化結果が空になり、`synthesize_wav` が 1 フレームも書かず、`wave` が close 時にチャンネル数が 0 のままであることに気づいてこのメッセージを投げます。ログ上の対応する実信号は `JPCommonLabel_make(): No phoneme` です。

現在は三道の防御があります。`strip_for_tts()` が `SPEAKABLE`（仮名/漢字/英字/数字）で判定し、発音可能な文字がなければ合成に送らずスキップ。`synth_to()` はメモリへ合成した後まずフレーム数を見て、0 フレームなら別の声質で再試行。それでも 0 なら読みやすい `ValueError` を投げます。

**② 中国語の応答内の数字が日本語で読まれる** —— 数字だけの文（`1.5`、`2026`、`OK`）は仮名も漢字もないため、以前は `default`（日本語）に落ちていました。その結果「3.14」が「さんてんいちよん」になっていました。現在は `pick()` が `hint` を受け取り、こうした文は直前の文で確定した声質に従います。`TurnRunner` は毎ターン `--reply-lang` で初期化し、各文の合成後に更新します。文脈がない場合のみ中国語に戻ります。

ついでに文分割も直しました。`SENT_END` の `.` が `3.14` や `v2.0` を真ん中で切っていたため、現在は `(?<!\d)\.(?!\d)` を使い、小数点の両側が同時に数字でないことを要求します。

### 4.5 ウェイクワード（常時リスニング）

ページ上で「常時リスニング」を押すと、以降は **「小八你好」** と言うだけで会話を開始でき、マウスに触る必要はありません。

使っているのは `sherpa-onnx-kws-zipformer-wenetspeech-3.3M-2024-01-01`。中国語ピンインでモデル化され、3.3M パラメータ、CPU のみです。

| 指標 | 実測 |
|---|---|
| RTF | 0.030（8 秒の音声を 0.26 秒で処理、単一コアの約 3%） |
| 誤発火 | 通常の中国語音声 14 区間（ニュース/インタビュー）で 0 回 |
| カスタム語 | 漢字 → ピンインは `text2token` が実行時に生成、語の変更に再学習は不要 |

**なぜ `AudioHub` が必須なのか**：ウェイクワードはマイクを常時開いておく必要があり、ALSA デバイスは同時に一つのプロセスしか占有できません。以前は `record()` が毎回自分で `arecord` を起動していたため、ウェイクアップスレッドが動き出すとデバイスを取り合っていました。現在は一つのスレッドがデバイスを独占し、20ms の固定長フレームを購読者に配信します：

- 購読時には直近 0.3–0.6 秒のフレームを先に補填 → 「小八你好，今天天气怎么样」と続けて言っても語頭が落ちない
- キューが満杯なら最も古いフレームを捨て、収音スレッドが遅い消費者にブロックされない
- `arecord` が異常終了したら自動で再起動（`/api/health` の `hub.errors` で観測可能）

ブラウザ側は**長接続を使わず、400ms のショートポーリング**（`GET /api/poll?after=<seq>`）。以前は `GET /api/live` の NDJSON 長接続でしたが、このアクセス環境ではまったく確立できず（サーバー側の `live` が常に 0）、ウェイクワードのヒット 7 回すべてが「聞いているページがない」と判定されてスキップされました。ショートポーリングは通常の fetch なので、どんなプロキシ環境でも通ります。代償はウェイクから通知音まで最大 400ms の遅延です。

サーバー側は 600 件のイベントリングバッファと自動増加するシーケンス番号を保持し、ページを開いたときは `after=` に極大値を渡して現在位置に合わせ、過去のイベントは再生しません。ウェイクのターンと手動のターンは同じ `turn_lock` で排他され、同時にマイクを取り合うことはありません。

> ウェイクワードは中国語のみです。公式 KWS モデルは wenetspeech（中国語ピンイン）で学習されており、日本語の発音は合いません。将来日本語のウェイクワードが必要になれば、「常駐 SenseVoice 認識 + テキストマッチング」に戻すしかなく、CPU 使用率は 3% から 10% 程度に上がります。

### 4.6 割り込み（読み上げ中の発話）

アシスタントがまだ話している最中に口を挟むと、話し終わるのを待たずに即座に止めて聞き始めます。

**なぜ読み上げクロックが必要なのか**：合成は再生より一桁速く（RTF 0.1）、`TurnRunner.run()` が返った時点では前半のいくつかの区間がまだブラウザで再生待ちの列に並んでいます。「生成終了」で判定すると、ユーザーがアシスタントの話している最中にすでに「話し終わった」と扱われ、割り込みの窓がまったく存在しません。そこでサーバー側で仮想的な再生タイムライン（`SpeakState`）を維持し、音声を一段送るたびに終了時刻を `audio_s` 秒だけ後ろへ押し、キューが空になれば自然にゼロへ戻します。

判定チェーンは三道で、どれか一つでも通らなければ割り込みません：

| 判定基準 | 役割 | デフォルト |
|---|---|---|
| エネルギー | 無音のノイズフロア + マージンより高い | `--barge-db -42`、`--barge-margin 8` |
| 音声確率 | Silero VAD、キーボード/椅子/ファンを除去 | しきい値 0.5、0.30s 連続が必要 |
| テキスト重複 | スピーカー出力時の自己回り込みを除外 | 最長共通部分文字列 ≥3 文字かつ比率 ≥0.7 |

**第三道が要**です。スピーカー出力ではマイクがアシスタント自身の声を拾うため、除外しないと自己発振します。読み上げるたびに割り込まれ、読み直すたびに自分に割り込まれる、という状態です。回り込みの窓は 1〜2 秒しかなく、認識結果は三〜五文字（実測 `今天天`）。これと十四文字の全文で `SequenceMatcher.ratio` を取ると 0.35 にしかならず、しきい値には永遠に届きません。「最長共通部分文字列の比率」に変えると `3/3 = 1.0` となり、判定は明快です。

実装上の細かい点：

- **しきい値は無音のノイズフロアだけを追う**。読み上げ中のレベルは参照しない —— 回り込みと人間の音量はもともと同程度で、レベルでは区別できず、それでしきい値を上げると人間の割り込みも通らなくなる
- **回り込みと判定したら 1.2 秒クールダウン**。そうしないと同じ文を 0.3 秒ごとに再判定し、十数回むだに ASR を回すことになる
- **フレームの引き継ぎ**：割り込み検出がすでに読み取った 1.2 秒分のフレームを `hub.subscribe(pre_frames=...)` でそのまま録音へ渡す。ユーザーのその文の冒頭が失われない（リングバッファは 0.6 秒しかないので補填では戻せない）
- **中断されたターンは履歴に入れない**（`done.interrupted`）。不完全なものを残すと以後の文脈を汚す
- 読み上げが終わって非読み上げ期に戻ったら VAD を再構築する。そうしないと前の文の残留状態で次のターンの holding が歪む

実測（真の VAD + 真の ASR + 真の TTS、合成音のフレームをマイクの代わりに投入）：

| シナリオ | 結果 |
|---|---|
| スピーカー出力の回り込み | 2 回とも回り込みと判定、割り込み 0 回 |
| 人が「等一下，我还想问个问题」と割り込む | 割り込み 1 回、新ターン開始、イベントと LLM 呼び出しが各 1 回 |
| 2 秒の無音 | 一切反応なし |
| 再生終了後に発話 | 判定しない（読み上げクロックがゼロ） |

再現：`../asr-venv/bin/python tools/barge_e2e.py`（マイク不要、約 8 秒）。

**制限**：割り込みは常時リスニングモードでのみ有効です。手動で「話し始める」を押した場合は録音デバイスを `record()` が独占し、傍受チャネルがありません。またヘッドセットの方が確実です —— スピーカー出力では回り込みは除外されますが、クールダウン期間中は割り込めません。

```bash
--no-barge              # 割り込みを無効化
--barge-db -38          # 環境が騒がしいときにしきい値を上げる
--barge-margin 12       # ノイズフロアの変動が大きいときにマージンを増やす
```

観測：`/api/health` の `barge.hits`（割り込み回数）、`barge.echo`（除外された回り込み回数）、`barge.thr_db`（現在のしきい値）、`barge.playing` / `remain_s`（読み上げクロック）。ヒットと回り込みはいずれも journal に出ます：`[barge] 打断：「…」` / `[barge] 疑似串音，忽略：「…」`。

## 4.7 HDMI キャプチャカード（MacroSilicon MS2109）

経路：**信号源 → 4K USB KVM → キャプチャカード HDMI IN → USB → Jetson**。2026-11-19 に開通し、1080p30 で安定して映像が出ています。

| 項目 | 値 |
|---|---|
| デバイス | `534d:2109 MacroSilicon USB3.0 Capture`、UVC 1.00 |
| ノード | `/dev/video0`（映像）、`/dev/video1`（metadata） |
| 現在の接続点 | 4 ポートドックの第 **4** ポート → システム `1-4.4`（Bus 001 / 480Mbps） |
| フォーマット | MJPEG + YUYV、1920×1080 ~ 640×480 の計 11 段階 |
| 実能力 | HDMI 入力は 4K@30Hz まで；UVC 出力の上限は 1080p30（MS2109 は USB2.0 チップで、「USB3.0」は HDMI 側を指す） |

### 最大の罠：デバイスを開くたびに約 1.2 秒のウォームアップ黒フレームが出る

**MS2109 はデバイスを開くたび、および解像度を切り替えるたびに、最初の 33~36 フレームが必ず真っ黒（YMAX=7）になります。**

実測（640×480 で 40 フレーム連続取得）：最初の 33 フレームが `YMAX=7`、34 フレーム目から `YMAX=255`。

1 フレームだけ取って信号の有無を判断する人（私もそうでした）は、必ず「信号なし」という誤った結論に至ります —— 取れるのは常にウォームアップの黒フレームだからです。さらに紛らわしいのは、これが現象を帯域とまったく逆に見せることです。`640×480` は全黒、`1920×1080` の方が 9/10 で映像が出ます。低解像度の回は切り替えた直後でウォームアップが足りていないからです。

正しいサンプリング方法（1 回のオープン内でウォームアップフレームを捨てる）：

```bash
ffmpeg -f v4l2 -input_format mjpeg -video_size 1920x1080 -framerate 30 -i /dev/video0 \
       -t 2.5 -vf "select=gte(n\,40)" -frames:v 1 -y shot.jpg
```

### ウォームアップ後の安定性

10 秒 / 300 フレーム連続取得：最初の 36 フレームが黒、その後 **264 フレームはすべて正常で、途切れゼロ**。まれに `EOI missing, emulating` / `overread 8` が出ます（ハブ帯域の限界付近で壊れた JPEG で、ffmpeg が復旧できる）が、映像には影響しません。

### 切り分けの順序（次回はこれに従う）

1. `lsusb | grep 534d` —— 出なければ列挙の問題（給電、ポート変更、書き込み用 USB-C ポートを使っていないかを確認）
2. `/dev/video*` が存在するか —— カードはあるのにノードがない場合は通常 uvcvideo がバインドされていない
3. `tools/hdmi_probe.sh` を実行（ウォームアップ破棄を内蔵）—— これが信号なしと言って初めて本当に信号なし
4. それでも信号がなければ次を確認：HDMI ケーブルが IN ポートに挿さっているか、源がついているか、KVM がそのチャネルに切り替わっているか、4K@60 が上限を超えていないか

### 踏んだ給電の罠

同じカードをドックの第 3 ポートに挿すと、列挙は成功するものの **166 秒後に自分から切断**しました。第 4 ポートに変えてからは連続 8 分間ドロップなし。バスパワーのハブにヘッドセット + マウス + キャプチャカードでは給電が厳しく、長時間のキャプチャには本体の Type-A ポート（`1-1` / `1-2`）へ直挿しすることを勧めます。

## 4.8 画面を見る（フレーム抽出 → OCR → 会話へ）

アシスタントが「画面に何が書いてあるか」に答えられるようにします。経路：**キャプチャカードでフレーム取得 → ウォームアップフレーム破棄 → 1440 に縮小 → RapidOCR → user message に連結**。

```bash
python vision.py --image shot.jpg        # ハードウェア不要、OCR を直接テスト
python vision.py --dev /dev/video0       # 実デバイスから 1 フレーム取得して認識
curl -X POST -d '{"force":true}' localhost:8095/api/look   # サービス経由
```

### 二つのトリガー

| トリガー | 動作 |
|---|---|
| 「看看屏幕上是什么」などと話す | `is_look_intent()` がヒット → まず「我看一下。」と読み上げ → OCR → 画面テキストと一緒に LLM へ問い合わせ |
| ページの「画面を見る」ボタン | フレーム取得 + OCR のみ実行し、結果を「画面テキスト」カードに表示。LLM は呼ばない |

### なぜ PaddleOCR ではなく RapidOCR なのか

同じ 1080p の中国語画面（50 行）を Jetson 上で実測：

| エンジン | 所要時間 | 平均信頼度 |
|---|---|---|
| **RapidOCR (onnxruntime)** | **6.2s** | 0.894 |
| PaddleOCR デフォルト server モデル | 17.0s | 0.98 |
| PaddleOCR mobile | 24.6s | 0.749 |

mobile モデルは Jetson ではむしろ遅くなります（CPU は大きな畳み込みが苦手）。信頼度も落ちました。RapidOCR はさらに paddle の数百 MB の依存を省けます —— asr-venv にすでに入っています。

### なぜ入力を先に 1440 へ縮小するのか

| 入力 | 所要時間 | 結果 |
|---|---|---|
| 1920 | 7.3s | 「窗口」を「官口」と誤読 |
| **1440** | **5.7s** | 「窗口」を正しく読む |
| 1280 | 4.6s | 誤りが出始める |
| 960 | 4.3s | 小さい字が潰れる（「编辑」→「编冀」） |

RapidOCR は内部で長辺を固定サイズへ圧縮するため、先に自分で INTER_AREA で縮小すればリサンプリングを一度減らせ、むしろ精度が上がります。

2026-11-21 に実機フレーム（132 行の密なテキスト）で解像度を下げる道を再測定し、**結論は「やらない」**：

| 長辺 | 所要時間（同条件・4 スレッドで交互測定） | 行数 | 信頼度 |
|---|---|---|---|
| **1440** | 6.13s | 132 | **0.951** |
| 1200 | 5.94s | 134 | 0.942 |
| 1080 | 5.70s | 132 | 0.922 |

7% しか節約できず、信頼度は 0.03 落ち、行数も安定しません。**行数が多いときの所要時間は「行数 × 行あたりのデコード」で決まり、入力の画素数では決まりません** —— 面積から計算した利得はまったく実現しません。

この法則は後に二組のデータで確定しました（同一マシン、同じ 8 スレッド、同じ 1440 幅）：

| 画面の行数 | OCR 所要時間 | 1 行あたり |
|---|---|---|
| 132 行（IDE 全画面） | 4.24s | 32 ms |
| 53 行（別ウィンドウに切替） | 1.61s | 30 ms |

**したがって「画面を見るのを速くしたい」= 「画面の行数を減らす」**であり、解像度ともエンジンのパラメータとも関係ありません。

### 実測（音声経路込み、2026-11-21 実機、HDMI に映像あり）

```
LOOK: ok=True 行=130 置信=0.949 4.45s
DONE: look_s=4.45 llm_first_ms=1001 llm_s=2.0 total_s=6.56
```

フレーム取得の常駐化が効いた後に二巡再測定、**エンドツーエンド 6.56s / 7.30s**（以前の推算 6.3s とほぼ一致、やや楽観的だった）：

| 区間 | 第 1 巡 | 第 2 巡 | 比率 |
|---|---|---|---|
| フレーム取得 | 0.08s | 0.06s | ~1% |
| **OCR** | **4.34s** | **5.55s** | **68%~77%** |
| LLM 初回トークン | 1.00s | 0.45s | コールド / ホット（プレフィックスキャッシュヒット） |
| LLM 全体 | 2.00s | 1.59s | — |
| 初回文の TTS 合成 | 0.10s | 0.07s | ~1% |

結論：**フレーム取得は無視できる水準まで圧縮済みで、OCR が唯一のボトルネックであり、しかも自身の揺らぎが ±1.2s ある**。LLM の初回トークンはコールドで 1 秒、ホットで 0.45 秒。130 行の OCR テキストは毎回変わるため、プレフィックスキャッシュが効くのは system prompt の部分だけです。

> これは**CPU のみ**の数値です。rec を TensorRT に変えた後、エンドツーエンドは **3.4~3.9s** まで下がります。下の「rec を GPU へ」を参照。

### キャッシュでは救えない：画面は常に変化している

`look()` には dHash キャッシュがあります（8 秒以内の同一画面なら直接返す）。しかし実機で `force=false` を三回連続テストすると `cached` は**すべて False**、行数も 130/133/132 の間で揺れます —— IDE のカーソル、タイムスタンプ、ターミナル出力が常に動いているからです。

したがって「同じ画面を繰り返し見れば 4 秒節約できる」という仮定は**成立しません**。音声トリガーで `force=True` を使い続けるのが正解です。

### OCR のスレッド数：明示的に固定する必要がある（2026-11-21）

`RapidOCR()` にスレッド数を渡さないと onnxruntime のデフォルト値になります。同じ実機画面、同一プロセスで逐次測定：

| スレッド | 所要時間 | 行数 | 信頼度 |
|---|---|---|---|
| 6 | **4.34s** | 132 | 0.951 |
| **8** | **4.49s** | 132 | 0.951 |
| 10 | 5.11s | 132 | 0.951 |
| 12（=コア数） | **9.10s** | 132 | 0.951 |

**12 スレッドは 8 スレッドより二倍遅い** —— このマシンは vLLM、ASR、字幕サービスを同時に動かしており、12 スレッドは 12 コアをすべてオーバーサブスクライブします。スレッドマイグレーションとコア奪い合いのコストが並列化の利得をはるかに上回ります。平坦域は 6~8、10 から劣化し始め、12 で一気に崩れます。

現在 `vision.OCR_THREADS = 8` に固定し、`--vision-threads` で調整できます。注意：**本番の従来のデフォルト値もすでに 8 の近辺でした**（実測はずっと 4.0~4.5s で、9s ではありません）。したがってこの変更は**劣化防止のための強化**であり、高速化ではありません —— 機種変更、onnxruntime のバージョン変更、コア数の増加のときに突然二倍遅くなるのを防ぎます。

> 反例からの教訓：最初の比較では三つの設定を同時に走らせた結果、1200/1080 が 1440 より二倍遅くなりました。原因はベンチマーク自身の onnxruntime も 12 スレッドを起動しており、「二つのプロセスが取り合う」状態を測っていたからで、解像度を測っていたのではありません。**並行性に敏感なものを測るときは、必ずスレッドを制限し、設定間に間隔を空ける。**

### なぜ rec は CPU ではこれ以上下げられないのか（七つの道、すべて試した）

まず思い込みやすい判断を一つ正します。**RapidOCR の rec はもともとバッチ処理**であり、「一行ごとに一呼び出し」ではありません。`TextRecognizer.__call__` が受け取るのは crop の**リスト**で、`rec_batch_num`（デフォルト 6）ごとに一つの `norm_img_batch` にまとめて session へ送ります。したがって「複数行をまとめて一批にする」という最適化の方向は最初から存在しません。

所要時間の内訳（132 行の実機画面、8 スレッド）：

| 段階 | 所要時間 | 比率 |
|---|---|---|
| det | 0.297s | 7.6% |
| cls | 0.153s | 3.9% |
| **rec** | **3.437s**（25 バッチ × batch 6、147 ボックス） | **88.4%** |

次に一つずつ試しました：

| 試行 | 結果 | 判定 |
|---|---|---|
| `rec_batch_num` 6 → 12 / 24 / 48 | 4.03 → 4.13 / 4.01 / 4.85s | ❌ 利得なし、48 はむしろ崩壊（`max_wh_ratio` がバッチ内最大を取るため、バッチが大きいほどパディングが広がる） |
| `use_cls` を切る | -0.15s | ⚠️ わずか 4%、しかも逆さテキストの保護を失うので割に合わない |
| int8 全量子化 | 10.8MB → 2.9MB | ❌ **精度崩壊**：132 行 → 9 行、平均スコア 0.951 → 0.563（CTC は logits に極めて敏感） |
| int8 を MatMul のみ量子化 | 精度 132 行 / 0.951 / 1846 文字、**完全に無損失** | ❌ 速度 3.98s、まったく速くならない |
| PP-OCRv6_small に変更 | 4.68s、精度はむしろ高い（135 行 / 0.971 / 1976 文字） | ❌ 15% 遅い |
| `unclip_ratio` 1.6 → 1.2 / 1.0 | 4.69 / 5.14s | ❌ ボックスが tight になるほど遅い（直感に反する） |
| 定数畳み込み `Constant` → `initializer` | 3.90s（-4%、精度は文字単位で一致） | ➖ 利得≈測定ノイズ（±0.2s）、カスタムモデルファイルを保守する価値はない |
| CUDA EP | システム CUDA は **13.2**、ORT は **cu12** の wheel しか出していない。`pip` に cu13 パッケージはなく、`apt-cache` にも `cuda-cudart-12-*` がない | ❌ この道は ORT を自前ビルドしないと通れない |

結論：**rec を CPU で無損失に高速化する余地はない**。本当の出口は GPU だけ —— 以下を参照。

#### ついでに記録：Paddle2ONNX の罠

`ch_PP-OCRv4_rec_infer.onnx` では **initializer の数 = 0 で、420 個の重みがすべて `Constant` ノード**です。ORT の `quantize_dynamic` は initializer しか認識しないため、そのまま実行すると `Expected conv2d_157.w_0 to be an initializer` で落ちます。先に定数畳み込み（`Constant` の tensor を `graph.initializer` へ移し、ノードを削除）を行って初めて量子化が実際に重みへ作用します —— そうしないと「ファイルサイズがまったく同じ」という偽の成功を得るだけです。

### rec を GPU へ：TensorRT（2026-11-21）

**onnxruntime の CUDA EP は使わないこと。** このマシンは JetPack 7.2 + CUDA **13.2** ですが、ORT 公式は **cu12** の wheel しか出していません。pip に cu13 パッケージはなく、`apt-cache` にも `cuda-cudart-12-*` がありません。`onnxruntime-gpu` を入れると `get_available_providers()` は**ちゃんと** `CUDAExecutionProvider` を列挙します（嘘ですが）が、session を作ると `No registered plugin EP device found` で落ちます —— これは EP の .so の dlopen 失敗です。ここで時間を浪費しないでください。

TensorRT 10.16 はシステムに同梱されています（`libnvinfer.so.10` + `trtexec` + python `tensorrt`）。onnxruntime を迂回して直接 rec を走らせます。

**方法**：RapidOCR のソースは変更せず、`TextRecognizer.session` を `trt_rec.TrtRecSession` に差し替えるだけ。これにより `resize_norm_img`、CTC デコード、文字表はすべて元の実装を再利用し、両者の違いは推論バックエンドだけになるので、測れるのは純粋なバックエンド差です。

| バックエンド | OCR 合計（132 行） | 行数 | 平均スコア | 行単位の一致 |
|---|---|---|---|---|
| CPU (onnxruntime) | 4.12s | 132 | 0.951 | 基準 |
| **TensorRT FP16** | **1.17s（3.5×）** | 132 | 0.952 | 128/132 |

エンドツーエンド（音声で「屏幕上是什么」と質問、140 行）：**6.56s / 7.30s → 3.87s / 3.41s**。残りの時間は主に LLM 生成（2.1s）で、OCR はもうボトルネックではありません。

行単位の差は `θ.98 → 8.98`、`—a → 一a`、`误。 → 误触` のような単字の揺れだけで、FP16 と CPU FP32 の通常の差であり、「画面を読む」ことには影響しません。

#### engine はどう作るか

```bash
trtexec --onnx=<rapidocr>/models/ch_PP-OCRv4_rec_infer.onnx \
        --saveEngine=models/rec_fp16.engine --fp16 \
        --minShapes=x:1x3x48x256 --optShapes=x:6x3x48x320 --maxShapes=x:32x3x48x2048 \
        --memPoolSize=workspace:1024 --timingCacheFile=/tmp/trt_cache.bin
```

Orin では約 **11~12 分**かかります（動的 shape の tactic 探索が非常に遅く、ログが長時間更新されませんが、固まったわけではありません）。

`optShapes` を 320 にしたのには根拠があります。75 バッチの幅の分布を実測すると、**76% がまさに基準の 320**（バッチ内に極端に長い行がなければ `max_wh_ratio` はデフォルトの 6.67 を取る）で、1536 を超えるものは 4% だけでした。したがって opt を小さい値にするのは、よく通る経路を最速にするためであり、「中間値」を選ぶためではありません。

> 初版では `max` を 1024/1536 に設定して両方失敗しました —— 画面に非常に長い行（パス、URL、長いコード行）があると、`max_wh_ratio` がバッチ全体を 1036、1656 まで押し広げます。**この数値は測ってから決める必要があり**、当て推量では必ず再ビルドになります（毎回 12 分）。

#### profile を超えたバッチは CPU へ戻す

`TrtRecSession` で `set_input_shape` が False を返したら、元の ORT session に渡します。理由は、極値のために max 3000+ の engine を作り直すと 96% の通常バッチが遅くなるからで、その 4% に遅い道を歩ませた方がましです。`/api/health` の `vision.trt.fallback_pct` がその比率で、**正常時はほぼ 0 になるべき**です（profile を正しく決めた後の実測は 0 回フォールバック）。

#### 実行時依存：`cuda-python`（探索の残骸としてアンインストールしないこと）

`TrtRecSession` は自分で VRAM を確保し stream を設定しますが、それを支えるのが `cuda-python` です：

```bash
asr-venv/bin/pip install cuda-python
# 自検（約 1 秒）
asr-venv/bin/python -c "from cuda.bindings import runtime as rt; e,p = rt.cudaMalloc(16); print(e,p)"
# → (<cudaError.cudaSuccess: 0>, <cuda.bindings.runtime.cudaDevicePtr...>)
```

**これは `onnxruntime-gpu` とは無関係な別物**で、混同しないでください。ORT の CUDA EP はこのシステムでは死んでおり（CUDA 13.2 に対して wheel は cu12 のみ）、TensorRT の道は通ります —— まさにそのため、`cuda-python` は現在 rec を GPU に載せる唯一の依存です。

アンインストールしても**エラーは出ず**、**静かに** CPU へ戻るだけです。`/api/health` の `vision.trt.backend` が `cpu` になり、OCR は 1.17s から音もなく 4.12s に戻ります。環境を整理するときはこれを覚えておいてください。

API の細部が二つあります（どちらも踏みました）：`cudaMalloc` は `(err, ptr)` のタプルを返すので二つの値に展開する必要があり、`cudaFree` は `err` だけを返します。

#### 有効化

```bash
# models/rec_fp16.engine をデプロイディレクトリに置き、その後
voice_server.py ... --vision-trt /path/to/models/rec_fp16.engine
```

`--vision-trt` を渡さなければ CPU で動き、挙動は従来とまったく同じです。engine のロード失敗、TRT バージョン不一致、ファイル不在 —— すべて握りつぶして CPU へ戻し、「画面を見る」全体が使えなくなることは決してありません。起動時にバックグラウンドスレッドが先に engine を構築します（実測 3 秒）。そうしないと初回の画面取得で CUDA context の分だけ余計に待ちます。

**engine は TensorRT のバージョンに固定されます**：JetPack の変更や TRT のアップグレード後は必ず再ビルドが必要で、そうしないとデシリアライズに失敗します（その場合は自動で CPU に戻り、クラッシュはしません）。

> vLLM との共存は問題ありません。Orin は統合メモリで、vLLM が常駐約 7GB、TRT 推論は数百 MB しか使いません。実測で両者を同時に動かしても OCR と LLM は正常でした。ただし**engine のビルド時には 30GB+ を消費**して profiling を行うので、その数分間は他のタスクに VRAM を奪わせないでください。

### フレーム取得の常駐化：ウォームアップは一度だけ（2026-11-21）

旧実装は `grab()` のたびに `cv2.VideoCapture()` でデバイスを開き、40 フレームを捨ててウォームアップしていました。**画面を見るたびに固定で 1.2 秒を払う**うえ、`look()` はフレーム取得の後にキャッシュを確認する順序だったので、画面が変わっていなくても同じコストを払っていました。現在は `_Capture` がハンドルを常駐させます：

| | 旧（毎回開閉） | 新（常駐） |
|---|---|---|
| デバイスを開く + ネゴシエーション | 毎回 | **プロセス起動時に一度**（`prewarm()` をバックグラウンドスレッドで） |
| 40 フレームのウォームアップ | 毎回 1.2s | open ごとに 1 巡、通常は全期間で 1 巡のみ |
| フレーム取得ごと | 2.87s | **2 フレーム読み、約 0.07s** |

「バックグラウンドスレッドで連続デコード」をしないのは意図的です。1080p MJPG のデコードは継続的な CPU コストであり、「画面を見る」は 1 回のセッションで数回しか使わないからです。`BUFFERSIZE=1` によりドライバは常に一つのバッファだけを保持して上書きし続けるので、読んだものがそのまま現在の画面になります。したがって連続読みで鮮度を保つ必要はありません。

自己修復の規則が三つあります：

1. **フレーム読み取り失敗 → 一度解放して開き直す**（`reconnects` をカウント）。ドックの 166 秒断流はこれで復帰し、サービスの再起動は不要です。
2. **全黒 → ウォームアップを一巡追加してから判定**。源が解像度を切り替えると MS2109 は黒フレームを吐き直します。常駐ハンドルでは open は起きないのに「ストリーム途中で黒くなる」ことは起きるので、補わないと「HDMI に信号なし」と誤報します。
3. **`--vision-idle-release` 秒のアイドル後にデバイスを解放**（デフォルト 0 = 解放しない）。他のプログラムにこのキャプチャカードを使わせたいときは 300 などに設定します。

`GET /api/status` の `vision.capture` で `opens / warmups / reads / reconnects / open_s / grab_s` が直接見えます：**`opens` は 1 のままであるべき**で、増えていれば途中で切断・再接続があったということです。

### 三道の保護

1. **ウォームアップフレーム**：`_Capture` は open ごとに固定で 40 フレームを捨てる（4.7 参照）。そうしないと黒画像を掴み、OCR 結果が空になる
2. **信号なしは blank と判定**：基準は「暗くて平坦」——`mean < 12 かつ std < 6`。旧基準の `mean < 3` は実機では決してヒットしません。MS2109 は信号なしのとき **mean 7.0 / std 1.5** のフレームを吐く（YMAX=7 にセンサーノイズが乗る）ため、「文字のない画面」とみなされ、`ok=True, lines=0` という偽の合格を返していました。blank 判定の前にはウォームアップを一巡追加して再確認し、源の解像度切替時の誤報を避ける
3. **見えなければはっきり言う**：OCR で文字が取れないときは空のコンテキストを詰め込まず、明確にエラーを返す。モデルが想像で作文するのを防ぐ

### 既知の制限

- 結果は **3.4~3.9 秒**（rec を TensorRT にした実測）。内訳は **フレーム取得 0.08s + OCR 0.76~1.56s + LLM 初回トークン 0.2~0.6s + 生成 2.1s**。ボトルネックはすでに LLM 生成へ移り、OCR ではありません
- `--vision-trt` を付けない場合は CPU に戻り、エンドツーエンド 6.5~7.3 秒
- LLM の部分を縮めたいなら、**OCR から prompt へ送る文字数を削る**方がモデル交換より有効です。コールド prefill は約 0.58 ms/token で、1.6K 文字なら 1 秒、3.3K 文字なら 2 秒近くかかります。27B に変えるとこの項目が 1 秒から 8 秒になります（4.14 参照）
- OCR 待ちの間は **barge-in が効きません**。その時点は読み上げ中ではなく、割り込み監視が起動していないため、ユーザーが口を挟んでもこのターンが終わるまで待ちます
- OCR には安定した誤字があります（帧 → 顿、Jetson → letson、引用符の欠落）。system prompt で LLM に「文脈から補正」させ、訂正モデルは作りません
- 画面テキストが 1400 文字を超えると切り捨てられます（`max_chars`）

## 4.9 文字は出るが音が出ない（ブラウザの自動再生ブロック）

症状：ページ上にテキストの回答は正常に出るのに、**音がまったく出ず、エラーも何も表示されない**。

根本原因はサーバー側ではありません。1 ターン分を実測すると：

| 確認項目 | 結果 |
|---|---|
| サーバー側 TTS | ✅ 2.38s の wav を合成、`mean -15.1dB / max 0dB`、無音ではない |
| `GET /audio/xxx.wav` | ✅ 200、`audio/wav`、105004 バイト |
| ブラウザ | ❌ `play()` が `NotAllowedError` を返し、旧コードの `catch(()=>{ playNext() })` が**このエラーを黙って握りつぶしていた** |

Chrome / Edge のポリシーでは、ページが一度もユーザー操作を受けていない場合、音声付きの `play()` は即座に拒否されます。ウェイクワードで連続対話する場合は最後まで一度もクリックしないため、毎ターン遮断されます —— テキストは普通に描画され、音だけがすべて失われ、画面上には異常がまったく見えません。

### 現在の対処

1. **もう黙らない**：`play()` が失敗し `name === 'NotAllowedError'` のとき、ページ上部にオレンジのバナー「ブラウザが自動再生をブロックしたため、このターンは音が出ません」を表示
2. **音声を捨てない**：遮断された URL をキューの先頭に戻し、解除後に続けて再生（以前はそのまま破棄）
3. **ワンクリックで自己診断**：「音声テスト」ボタンを追加 → `POST /api/say` で「声音测试，一二三。」を合成 → ブラウザで再生。成功すれば長さと声質を、失敗すれば具体的なエラー名を表示
4. **どこをクリックしても解除扱い**：バナー自体、およびページ上の任意のクリックで、未再生分の補播を試みる

```bash
curl -X POST -H 'Content-Type: application/json' \
     -d '{"text":"声音测试"}' localhost:8095/api/say
# {"ok":true,"url":"/audio/say_xxx.wav","tts_s":0.15,"audio_s":2.04,"voice":"zh"}
```

### 切り分けの順序

1. 「音声テスト」を押す —— 音が出れば自動再生ポリシーで、ページを一度クリックすれば解除される。出なければ次へ
2. バナーに出るエラー名を見る：`NotAllowedError` = ポリシーによる遮断、`NotSupportedError` = wav が取得できない（`/audio/` ルートを確認）
3. どちらでもなければ、**タブがミュートされていないか**（タブにスピーカーの斜線）、システムの出力デバイス、ヘッドセットが PC ではなく Jetson に挿さっているかを確認

### 音が HDMI へ行ってしまった（実際に踏んだ）

ブラウザは Windows のデフォルト出力デバイスに従います。このマシンのデフォルト出力は一時期 `UHD-SPLITTER` / `HD TO USB`（Display Audio エンドポイント）で、読み上げ音がすべて HDMI 経路へ入り、スピーカーからは一切鳴りませんでした。

二つの道があり、変更の大きさ順に：

| 目標 | 方法 | コスト |
|---|---|---|
| **ブラウザだけスピーカーへ**（推奨） | Win11 設定 → システム → サウンド → 音量ミキサー → Chrome を見つける → 出力を `スピーカー (SC-HC410)` に変更 | なし、何もインストール不要 |
| 同じ音を両方から同時に出す | Voicemeeter（A1/A2 の二出力）、または Stereo Mix + 聴取 | 仮想サウンドカードの導入 / 100ms+ の遅延 |

**ついでの落とし穴**：キャプチャカード MS2109 は USB Audio を備えており、Jetson 上にすでに `card 4: MS2109` が増えています。つまり PC の音が HDMI → KVM → キャプチャカード経由で Jetson に戻ってきています。現在は読み上げがブラウザ側なので影響はありませんが、**Jetson ローカルの `aplay` で読み上げる方式に変えた瞬間にループが形成され**、しかも barge-in が自分が流した音をユーザーの割り込みと誤認します。

## 4.10 会議字幕（caption_server.py）

会議中に会議音声をリアルタイムで中日二言語字幕にします。独立プロセス、独立ポート（8096）で、音声アシスタントとは**完全に分離**されており、それぞれ別の音源を使うので互いに干渉しません。

```bash
sudo systemctl start caption-bench       # 常駐サービス（enable 済み）
journalctl -u caption-bench -f           # リアルタイムログ
python caption_server.py --wav x.wav     # オフラインでファイル 1 本、ハードウェア不要
```

経路：`キャプチャカード音声 → エネルギーによる文分割 → SenseVoice(auto) → 中/日相互翻訳 → Web ページのスクロール大字字幕`

### 三つの罠（すべて踏んだ）

1. **PipeWire がデバイスを奪う** —— 最重要。MS2109 が PipeWire にデフォルト録音源として認識されると `pcmC4D0c` を長期間占有し、`arecord -D plughw:CARD=MS2109` は延々と「デバイスまたはリソースがビジー」になります。しかも `pgrep arecord` にはどのプロセスも見えません（占有者は `pipewire`）。`pw-record --target <node>` でストリームを取る方式に変えるとデバイスを独占せず、他の音声クライアントとも共存できます。ノード名は `pw-dump` から `MACROSILICON` で自動的に探します。
2. **systemd 内で pw-record が接続できない** —— システムサービスには `XDG_RUNTIME_DIR` がなく、user session の PipeWire socket が見つからず、プロセスは起動直後に終了します。unit に `Environment=XDG_RUNTIME_DIR=/run/user/<uid>` を必ず書きます。
3. **ノイズフロア初期値の汚染** —— 以前は `min(floor, db)` でフロアを推定していたため、最初にデジタル無音（-91dB）を拾うと floor が -999 に固定され、しきい値が -991dB になり、「どんな音も発話とみなさない」状態になりました。冒頭 1.2 秒の 10 パーセンタイルを取り、以後は速く下げてゆっくり上げ、`[-85, -32]` にクランプする方式に変更。

### ページ上の開始 / 停止

| ボタン | 動作 |
|---|---|
| **停止** | 収音プロセスを実際に terminate してサウンドカードを解放、ボタンが緑の「開始」に変わり、レベルはゼロに |
| **開始** | Segmenter を再構築（その時点の部屋でノイズフロアを再推定）して収音を再開 |
| クリア | 出力済みの字幕だけを消し、収音は止めない |

停止直後に開始を押すと USB サウンドカードの解放遅延に当たることがあり、内部で自動的に 4 回リトライします（間隔 0.35~1.1 秒）。

### パラメータ

| パラメータ | デフォルト | 説明 |
|---|---|---|
| `--backend` | `pw` | `pw`=PipeWire（推奨）；`alsa`=arecord 直結 |
| `--device` | `plughw:CARD=MS2109,DEV=0` | `--backend alsa` のときのみ使用 |
| `--margin` | `8.0` | フロアより何 dB 上なら発話とみなすか、騒がしい環境では大きくする |
| `--hold` | `0.45` | 基準の無音しきい値（区間長が `--seg-mid` と `--seg-long` の間のときに使う） |
| `--hold-long` | `0.90` | 区間がまだ短いときに、どれだけ無音なら切るか。4.16 参照 |
| `--hold-short` | `0.30` | 区間がすでに長いときの切断しきい値。4.16 参照 |
| `--seg-mid` / `--seg-long` | `1.20` / `2.40` | 上記二つのしきい値の切替点（秒） |
| `--max-s` | `6.0` | 1 区間の最大秒数、最終手段の強制切断（根拠は 4.16：7.0 にするとハルシネーションが出る） |
| `--soft-cut` | `0.7` | 強制切断の前にエネルギーの谷を探す後退探索窓（秒） |
| `--min-s` | `0.25` | 有声長がこれ未満なら捨てる |
| `--no-bilingual` | オフ | 原文のみ出力し、LLM 翻訳を呼ばない |

### 既知の制限

- **音楽は「文字」として聞き取られる**：SenseVoice は歌詞や純音楽に対してハルシネーションのテキストを生成します（実測ではある曲を「风从楼间穿过去…」と認識）。正確なのは人間の発話だけです
- 遅延 = 文分割待ち（0.55s）+ ASR（0.1~0.4s）+ 翻訳（0.3~0.8s）で約 1~2 秒。会議録としては十分、同時通訳としては低い
- 翻訳はローカルの qwen（7B）を通るので、長文や固有名詞は偏ります。原文に誤字があると訳文も引きずられます

### 4.11 読み上げの出口：ブラウザ vs 本体ヘッドセット

**症状**：ヘッドセットを Jetson の USB ポートに挿し、マイクも認識されている（`plughw:CARD=H340`）のに、アシスタントがヘッドセットから一度も音を出さない。

**根本原因**：読み上げは**ブラウザ**が再生します。`_speak()` は `emit({"type":"audio","url":...})` を出すだけで、ページを開いているマシンが wav を取得して再生します。つまり「音がどこから出るか」は「ページをどのマシンで開いているか」と等しく、マイクがどこに挿さっているかとは無関係です。実測ではページを PC（`127.0.0.1`）で開いているとき、`voice-bench` のマシン上には再生ストリームが一つもありませんでした。

**解決**：ローカル再生の経路 `LocalSpeaker` を追加し、合成後に直接 `pw-play` で本体のサウンドカードへ送ります。

```
合成 wav ─┬─ emit audio{local:true} → ブラウザは文字だけ表示、再生しない
          └─ LocalSpeaker.play()    → pw-play --target <H340> → ヘッドセット
```

**三つの設計点**

| 問題 | 方法 |
|---|---|
| なぜ `aplay` ではなく `pw-play` か | マイクは `AudioHub` が ALSA で排他占有しており、`arecord -D plughw:CARD=H340` は「デバイスまたはリソースがビジー」になる。再生は PipeWire を通り、収音とは USB サウンドカード上の二本の独立したストリームになるので取り合わない |
| 割り込みでどう止めるか | `LocalSpeaker.cancel()` でキューを空にし、現在の `pw-play` を `terminate()`。`BargeMonitor._on_barge()` 内で `SpeakState.cancel()` と一緒に呼ぶ |
| systemd 内で音が出ない理由 | 字幕サービスと同じ罠：`XDG_RUNTIME_DIR=/run/user/<uid>` がなく、`pw-play` が user session の PipeWire に接続できず即失敗する |

**切替**：ページに「音声：ヘッドセット / 音声：ブラウザ」ボタンを追加 → `POST /api/route {on:bool}`。実行中に切り替えられ、再起動は不要。`/api/say` の「音声テスト」もこのスイッチに従うので、「試聴で音が出るか」と「実際に音が出るか」が同じ経路になります。

**起動パラメータ**

| パラメータ | デフォルト | 説明 |
|---|---|---|
| `--local-speak` | オフ | ローカル読み上げを有効化 |
| `--local-sink` | 空（システムデフォルト） | PipeWire のターゲットノード名/id。例 `alsa_output.usb-Logitech_Inc._Logi_USB_Headset_H340-00.analog-stereo` |
| `--local-gain` | `1.0` | ストリーム音量 0~1 |

`/api/health` の `speaker` フィールドで `on / sink / plays / errors / busy / last_error` が見られます。`plays` は**終了コード 0** の再生だけを数えるので、「再生したが音が出ない」と「そもそも再生していない」を区別できます。

**切り分けの順序**：`speaker.plays` が増えている → 再生経路は通っているのでヘッドセット本体を確認（H340 のインライン音量ホイール、プラグが根元まで挿さっているか）。`plays` が動かず `errors` が増える → `last_error` を見る（ほとんどは `XDG_RUNTIME_DIR` か sink 名の誤り）。

### 4.12 HDMI から入ってきた音をヘッドセットへ回す

**シナリオ**：PC の HDMI 出力がすべてキャプチャカードへ入り（音も映像も Jetson へ）、人間には聞こえない。Jetson にもう一副ヘッドセットを挿し、この経路をそのまま再生すれば、HDMI リンクにモニタ端口を足したのと同じになります。

```
キャプチャカード source ──┬─ pw-record 16k  → 文分割 → ASR → 字幕
                          └─ pw-record 44.1k → pw-cat → ヘッドセット（モニタ）
```

二本の収音ストリームが併存します。PipeWire は複数クライアントが同じ source を読むことを許すので、実測で字幕側の 16k ストリームはまったく影響を受けませんでした。

**実装の要点**

| 問題 | 方法 |
|---|---|
| どう運ぶか | `pw-record \| pw-cat` の二つの子プロセスを直結。サンプルデータはカーネルのパイプだけを通り、Python は関与しないので CPU 使用率はほぼ 0 |
| なぜ `pw-link` でノード直結しないのか | 直結の方が遅延は低いが、デバイスを挿し直すとリンクが切れても通知がない。子プロセス方式なら切れた瞬間に `poll()` で分かり、再接続しやすい |
| サンプリングレート | ヘッドセットノードは **44100**、キャプチャカードは 48000。44100 に統一し、リサンプリングを一度省く |
| バッファ | `--latency 20ms` で両端各 20ms、エンドツーエンド約 60~100ms。実測で 20/40/デフォルトの三档ともアンダーランなし、20ms が最も追従が良い |
| スイッチ | ページの「HDMI を聴く」ボタン → `POST /api/monitor {on}`；`--monitor` ならサービス起動時に直接オン |

**検証方法**（音の話はプロセスが生きているだけでは判断できない）

```bash
# ポートが本当につながっているか：[active] が出て初めて転送中
wpctl status | sed -n '/Streams:/,$p' | grep -A2 pw-cat
# リアルタイムレートで読んでいるか：4 秒後に rchar が約 700KB 増えるはず
grep rchar /proc/$(pgrep -x pw-cat)/io
```

**罠**：`pw-top` では `pw-cat` とヘッドセットノードが `???`（quantum 0、rate 0）と表示され、動いていないように見えます。しかし `[active]` のリンクと `rchar` の増加が転送中であることを証明します。`???` はそのノードがグラフの driver ではなく、タイムスタンプが取れないというだけの意味で、**「音が出ていない」証拠にはなりません**。本当の判断材料は `wpctl status` の `[active]` とプロセスの IO カウントです。

**副作用（要注意）**：ヘッドセットから出る会議音は H340 マイクにも少し拾われ、ウェイクワードや割り込みを誘発する可能性があります。会議中に自問自答が起きたら、まず「HDMI を聴く」を切り、またはヘッドセットマイクなしのイヤホンに変えてください。

### 4.13 会議は「リアルタイム」でなければならない：8 秒を 1~2 秒へ

**従来の遅延の内訳**（実測）：1 区間は一律 6.0 秒（`max_s` の強制切断）→ 区間内で平均 3 秒むだに待つ → ASR 0.38 秒 → **翻訳 0.3~1 秒が認識スレッド内で直列実行**（その間、収音フレームはキューで待機）→ フロントエンドは 600ms ポーリング。話し終わってから文字が見えるまで **7~8 秒**で、同時通訳としては聞き手の感覚に追いつきません。

**四つの変更**

| 変更 | 従来 | 現在 | 効果 |
|---|---|---|---|
| 区間長の上限 `--max-s` | 6.0s | **3.0s** | 遅延のハード上限を半分に |
| 無音による切断 `--hold` | 0.55s | **0.42s** | 一文を話し終えてからより速く締める |
| 文字の出し方 | 訳し終わるまで待って行全体を出す | **原文は即出し、訳文はパッチで後追い** | 文字を見るまで ASR だけ待てばよい |
| スレッドモデル | 収音スレッド内で ASR + 翻訳を同期実行 | **収音 / ASR / 翻訳の三本の独立キュー** | どこか一环が遅くなっても収音が詰まらない |
| フロントエンドのポーリング | 600ms | **250ms** | 体感がより追従する |

**実測（音楽を流して連続的に有声）**：`lag_ms`（区間終了 → 原文が見える）は **96~190ms** で、そのすべてを `asr_ms` が占める。`trans_ms` が 217~756ms で後から補われ、`q_asr=0 / q_tr=0` は滞留がまったくないことを示す。話し終わってから原文が見えるまで約 **0.6~1 秒**（0.42s の無音判定 + ASR + ポーリング）、訳文はさらに 0.2~0.8 秒後。

**二段階方式の実装要点**

- `Captioner.submit()` はキューに入れるだけで、収音ループは認識を一切待たない。キューが満杯なら**最も古い区間を捨てる**。字幕がどんどん遅れていくよりましだから（10 秒遅れの字幕は無いのと同じ）。
- 認識が終わったら即座に `trans="" / pending=true` の行を append し、フロントエンドは「翻訳中…」のプレースホルダを表示する。
- 翻訳スレッドは計算後にその場で `line["trans"]` を埋め戻し（履歴にも新規ページにも完全な形で出る）、同時に `{seq, trans}` をパッチキューへ積む。`/api/poll` の `upd` フィールドで一度だけ下り、送信後クリアされる。
- フロントエンドは `seq` でパッチをマージし、再描画時にスクロール位置を保つ（最下部にいれば追従、途中を読んでいれば動かさない）。

**ついでに直した二つの品質問題**

1. **強制切断が音節の途中に入る**：`天真好` が `天真` で切られると「天空」と訳される。現在は `--soft-cut` の上限に達すると、末尾 0.7 秒以内で**エネルギーが最も低いフレームへ後退して**切れ目を入れ、残りのフレームを次の区間へ回す（区間長は 2.3~3.0 秒で変動するが、誤字はかなり減る）。
2. **短い文で訳文の言語が混ざる**：短く切ると単文が半文になることが多く、モデルが「的/了」を残したり中英日が混在したりする。翻訳 prompt を「訳文は純粋な目標言語でなければならず、原文の語を一つも残してはならない」という厳格な要求に変え、さらに**直前二文の原文を【上文】として**一緒に送ることで、人称と用語が合うようになった。
3. **フィラーが実詞として扱われる**（`strip_fillers()`）：会議では「嗯、呃、えーと、あの」が頻出し、モデルがこれを「はい」「ええ」「那个」と訳して文全体の意味を歪める。現在は**翻訳へ送る前**に純粋なフィラーを削除し、**ページに表示する原文は逐字のまま**残す（逐字稿自体に価値がある）。

クリーニング規則は意図的に保守的で、語彙リストで推測するのではなく「前後が必ず句読点か文境界であること」に頼ります。`那个项目` の「那个」、`あの人` の「あの」の後ろには実詞が続くので自然に一致せず、リストに入れなくても誤爆しません（`that is her eraser` の `er` も同様）。文全体がフィラー（例「哦。」）の場合は**原文に戻し**、空文字列を返すことは決してありません。

**パラメータ**

```bash
--max-s 3.0        # 遅延のハード上限；会議では 4 秒を超えないこと
--hold 0.42        # 何秒の無音で切るか；これより小さくすると語が二分割される
--min-s 0.25       # これ未満は捨てる（カチッという音）
--soft-cut 0.7     # 強制切断前に谷を探す後退探索窓
--asr-workers 1    # ASR は 1 区間 0.1~0.2 秒なので 1 で十分
--tr-workers 1     # 本番は 1：実測で 1 と 2 は初回トークンに差なし（4.21）、待ち行列が一段減る
--ctx-lines 1      # 本番は 1：上文を一句だけ渡し、初回トークンが 2 より ~90ms 節約（4.21）
                   # 訳文はデフォルトでストリーミング（初回トークン 260ms）；--no-stream-trans で全文一括に戻る
--tr-prompt full   # system prompt の档位；short は 35B の短縮版で、実測ではむしろ遅い（4.20 参照）
```

状態に `lag_ms / asr_ms / trans_ms / ttft_ms / q_asr / q_tr / dropped` が追加され、ページ上部に「遅延 x.x s · 初回トークン xx ms · 訳完了 x.x s」が直接表示されます。追いついているかは二つの数だけ見れば分かります：**キューが常に 0 ならリアルタイム**、`q_tr` が上がり続けるなら翻訳が追いついていないので `--tr-workers` を増やします。

> 「翻訳中」が逐字で出るようにしたい場合は **4.15** を参照（訳文ストリーミング + SSE プッシュ、初回トークン 260ms）。

**回帰テスト**：`test_caption_pipe.py`（ASR と翻訳をスタブ化、モデル非依存）。7 ケースで二段階の文字出し、パッチの重複排除、上文の受け渡し、投入がブロックしないこと、キュー溢れで最古を捨てること、短区間の上限、谷での切れ目、クリアをカバー。

### 4.14 モデルを替える前に測るべき三つの数（音声シナリオの判断基準）

Jetson 上で推論エンジンの比較を一巡行いました（llama.cpp vs Magnitude、1B / 27B × 8K / 32K）。結論は memmy にあります。ただし**あの数値はエージェント実行の口径**であり、そのまま音声アシスタントのモデル選定に使うと逆の答えが出ます：

| 次元 | エージェント実行（評価口径） | 個人用音声アシスタント |
|---|---|---|
| 並行性 | 数十回の呼び出しを直列につなぐ | **1 ユーザー、1 経路** |
| 1 回の出力 | 200–800 token | 一文、20–80 token |
| コンテキスト | 20K–60K、増えるだけで縮まない | 2–4K（人設 + 直近数ターン） |
| 重要指標 | 集約スループット、単位コスト | **プレフィックスヒット時の TTFT**、初回文の出声時間 |
| 遅くなったときの結果 | 実行に時間がかかるだけ | ユーザーは「聞こえなかった」と思う |

したがって評価で最も目を引く二つの数 —— Magnitude が N=8 で集約 12.17 tok/s、バッチ処理のスイートスポットが 4 路 —— は**アシスタントにはほぼ無用**です。8 並行など存在しないからです。

#### 三本のハードライン

| 基準 | ライン | 理由 |
|---|---|---|
| プレフィックスヒット TTFT | **< 300 ms** | 人設の system prompt は固定で毎ターンキャッシュに当たる。ここが本当の起点 |
| 単一リクエスト decode | **≥ 20 tok/s** | TTS は約 4~5 文字/秒。20 を下回ると「考えながら話す」ような息継ぎの間が入る |
| 初回文の出声（実測） | **< 600 ms** | 最初の句点または 12 文字まで。ユーザーが「分かってくれた」と感じる瞬間 |

**token 換算で初回文の遅延を見積もらないこと**：中国語の分詞は約 1.3 文字/token、7B を 26 tok/s として「20 token」を換算すると 769 ms になりますが、実際の初回文は 279 ms しかかかりません。初版の判断基準はここで失敗しました（不合格と誤判定）。

#### 同一マシンでの実測（Jetson AGX Orin 64GB、単一リクエスト、temperature=0、3 回の中央値）

| モデル | decode tok/s | プレフィックスヒット TTFT | コールド prefill TTFT | プロセス冷起動 | メモリピーク | 初回文出声 |
|---|---|---|---|---|---|---|
| Qwen2.5-7B-AWQ（vLLM、**現行**） | **26.0** | **88 ms** | 438 ms | —（常駐） | — | **279 ms** ✅ |
| 27B Q4（llama.cpp） | 7.74 | 309 ms | 7.85 s | 15.4 s | 29.1 GB | ≈2.6 s ❌ |
| 27B Q4（Magnitude） | 6.17 | 294 ms | 7.06 s | 148.4 s | 33.6 GB | ≈3.2 s ❌ |
| 27B Q4（Magnitude + DFlash2） | 20.19 | 280 ms | 7.50 s | 97 s | 34.3 GB | ≈1.0 s △ |
| 1B Q4（llama.cpp） | 111.8 | 26 ms | — | 2.1 s | 11.9 GB | ≈0.2 s ✅ |

**コールド prefill とプロセス冷起動は別物**です。前者は毎ターン起こり得ます（コンテキストが変われば再計算が必要）。後者はサービス再起動時に一度だけです。27B の 7.85 秒のコールド prefill だけで致命判定に足ります —— ユーザーが話し終えてから、prompt の再計算だけで 8 秒かかるのです。

#### 実際の prompt でスキャン：破綻するのは「画面を見る」だけ

上の表は固定の人設を使っています。`voice_server.py` の実際の 242 文字の system prompt に替え、四つの実際のコンテキストでそれぞれ実行（`tools/ttft_scenarios.py`、3 回の中央値）：

| シナリオ | コンテキスト | 初回トークン（warm） | 初回トークン（cold） | 初回文出声 | decode |
|---|---|---|---|---|---|
| 一問一答 | 172 tok | **86 ms** | 130 ms | 393 ms | 26.0 tok/s |
| 6 ターン履歴 | 335 tok | **86 ms** | 224 ms | 319 ms | 26.0 tok/s |
| 画面を見る 2K 文字 | 1661 tok | 91 ms | **1008 ms** | 435 ms | 26.2 tok/s |
| 画面を見る 4K 文字 | 3273 tok | 104 ms | **1944 ms** | 449 ms | 26.0 tok/s |

二つの結論：

1. **warm の初回トークンはコンテキストにほとんど依存しない**（86→104 ms、172→3273 token で 18 ms しか増えない）。プレフィックスキャッシュは本当に効いており、日常のマルチターン対話は常にこの水準です —— 十ターン話しても遅くなりません。
2. **cold の初回トークンはコンテキストにほぼ線形に増える**。傾きは約 **0.58 ms/token**（コールド prefill ≈ 1700 tok/s に換算）。したがって**画面を見るだけが 300 ms を破るシナリオ**です。OCR テキストはフレームごとに変わり、OCR の部分からすべて再計算になります。1.6K 文字で 1 秒、3.3K 文字で 2 秒近く。

これが画面を見るの所要時間の構成も説明します（CPU 版：フレーム取得 0.07 + OCR 4.3~5.6 + **LLM 初回トークン 0.45~1.0** + 生成）。さらに縮めたいなら、モデルを替えるのではなく OCR から prompt へ送る文字数を削る（分区 OCR / ウィンドウ本体だけを取る）のが優先です —— 27B に替えるとこの項目が 1 秒から 8 秒になります。

**判定**：27B を素で走らせて音声のホットパスには入れられません。「少し遅い」のではなく、初回文の出声に 3 秒かかり、4.13 で得た 1~2 秒の成果をすべて巻き戻します。一方 7B の 279 ms のうち LLM はごく一部で、ボトルネックは依然として文分割（0.42s）と ASR（0.19s）にあり、これが健全な構造です。

#### 档位の確定とエンジン

- **ホットパス（ウェイク応答、指示、雑談、切り替え）：1B–4B または 7B**。7B が現在のスイートスポットで、実測で全項目が基準を満たします。
- **コールドパス（画面 OCR 後の推論、会議議事録の後処理、長文書翻訳）：9B–14B / 27B**。ユーザーが 5–10 秒待つことを許容できる場合。
- ただし 1B はルーターとしてのみ使えます。実測で「投機デコード」を説明させると金融用語で答えてしまいました。人格を持たせた対話ではボロが出ます。
- **エンジンは llama.cpp を常駐させ、Magnitude は使わない**：冷起動 15.4s 対 148.4s（落ちても 15 秒で自己復旧できる必要がある）。Magnitude には **`n_ctx` のスイッチがなく**、1B でも 131072 で固定に KV を配分し 12.8GB を無駄に食う。llama.cpp は `-c 4096` で 3GB 強まで抑えられる —— 64GB の統合メモリは ASR / RapidOCR / vLLM とも取り合う。プレフィックスヒットも 26ms 対 141ms でタダ取り。
- Magnitude が価値を持つ唯一のシナリオは**どうしてもホットパスで 27B を使う**場合で、DFlash2 により decode を 20.19（2.6×）まで引き上げられる。
- **多重並行は vLLM に任せ、第三のスタックを持ち込まない**：アシスタントの実際の並行性は「音声 Q&A + 字幕翻訳 + バックグラウンド要約」であり、連続バッチ処理は vLLM の得意分野です。

#### 再測定の口径（口径のずれ防止）

```bash
# 任意の OpenAI 互換エンドポイント：vLLM / llama-server / Magnitude
../asr-venv/bin/python tools/llm_probe.py --base http://127.0.0.1:8000/v1 --model qwen --runs 3
# --json で構造化結果、終了コード 0=全項目達成、1=未達項目あり、そのまま CI に入れられる
```

スクリプトがやること：一度ウォームアップ（モデルのロード / kernel チューニングは計上しない）→ 同じ prompt で N 回、プレフィックスヒット状態を測定 → prompt の前に一意な nonce を付けて N 回、コールド prefill を測定 → 中央値とレンジを表示。判定はすべてスクリプト内にあり、自分で計算する必要はありません。

口径の要件（この何条かは数値より重要）：

1. **同一の GGUF に sha256 を添付**；量子化を変えたら横比較しない。
2. `temperature=0`、`seed=42`、各項目 **≥3 回の中央値**、レンジを**ノイズ下限**として記録；差がレンジより大きい場合に初めて真の差とみなす。
3. **プレフィックスヒット状態とコールド prefill を分けて測る**：コールド prefill は prompt の先頭に一意な nonce を付け、`cache_n=0` を確認する。
4. **投機デコードは両側を揃える**：両方オンか両方オフ。片方だけオンにして比べてはいけない（llama.cpp は 7d7f028 以降 `--spec-type` を内蔵しており、初期の「llama には等価な実装がない」はすでに成立しない）。
5. **単一リクエストで測る（`-np 1`）**；並行性は別の組として測り、同じ表に混ぜない。
6. 速度だけを測り品質は測らない —— **エンジンを替えても賢くはならず、スループットが変わるだけ**。

### 4.15 訳文ストリーミング + SSE：「0.8 秒待って一気に出る」を「0.26 秒から逐字で出る」へ

4.13 の仕組みで原文は 147ms まで圧縮されましたが、**訳文は依然として一文まるごと一度に出ていました**（`trans 296~1210ms`）。ユーザーから「ストリーミングにできないか」と問われ —— できます。しかも利得は予想より大きいものでした。

**まず何が遅いのかを測る**：vLLM の system prompt はプレフィックスキャッシュされるので、

| | 非ストリーミング（全文） | ストリーミング初回トークン | ストリーミング全文 |
|---|---|---|---|
| 短い文「元首和平宣言。」 | 368ms | **93ms** | 370ms |
| 長い文（20 文字） | 756ms | **88ms** | 759ms |
| 最長の文 | 1309ms | **88ms** | 1309ms |
| 6 例の平均 | 701ms | **96ms** | 690ms |

**要点**：初回トークンはわずか ~96ms なのに、全文には 700ms かかります —— 遅いのは**トークンごとの生成**で、prefill ではありません。つまりストリーミングは単に「速く見える」のではなく、**ユーザーが最初の一文字を見る時刻を 275~1221ms 前倒し**し、総所要時間はまったく変わりません。

#### エンドツーエンド実測（実際の HDMI 会議音声、810 区間の実行中）

| 指標 | 改修前 | 改修後 |
|---|---|---|
| 区間終了 → 原文 | 147ms | 147ms |
| 区間終了 → **初回トークンの訳文** | 830~1360ms（= 全文待ち） | **260ms** |
| 区間終了 → 訳文全出 | 830~1360ms | 808ms |

体感遅延は **3~5 倍**下がり、GPU 使用率は変わっていません（同じリクエストで、書き終わるのをブロックして待たないだけ）。

#### 実装の要点

1. **`translate_stream()`**：vLLM の `data:` ストリームを SSE で解析し、delta を受け取るたびにコールバック。`(全文, ttft_ms, total_ms)` を返す。例外時は**受け取った部分を保持する** —— 半文の訳文でも空白よりは役に立つ。
2. **増分ではなく累積テキストを送る**：フロントエンドの `applyUpd` はもともと `l.trans = u.trans` の行全体置換なので、累積文字列を送れば描画ロジックを変えずに済む。実測で 13/13 区間の各中間状態が最終訳文の**厳密なプレフィックス**だったため、置換でちらつかない。
3. **同一 seq のパッチをマージする**（`_push_update`）：フロントエンドは 250ms ポーリング、ストリーミングは 80ms ごとに増分が出る。マージしないと 1 回の poll で同じ行の中間状態を 3 本受け取り、2 回むだに再描画する。
4. **中間状態には `trans_ms` を付けず、`final` のときだけ付ける**：そうしないとページ上の「訳 x.x s」が延々と跳ね上がる。
5. **`--no-stream-trans` で全文一括に戻せる**。問題の切り分け時のみ使う。

#### 出力側：250ms ポーリング → SSE プッシュ

ポーリング自体が平均 125ms を上乗せします。`/api/events`（`text/event-stream`）に変えると中間状態が届いた瞬間に描画され、実測のプッシュ間隔は最短 **51ms**。

**マルチクライアントの罠を踏みました**：`take_updates()` は「取り出すと同時にクリア」なので、二つのページを同時に開くとパッチを取り合い、二つ目は永遠に「翻訳中…」で止まります。そこで SSE エンドポイントでは `take_updates()` を**使わず**、接続ごとに `{seq: trans}` のスナップショットを保持して差分比較します。検証方法は二クライアントの同時購読で、それぞれ **97 バージョン / 15 区間すべてに中間状態を含む**を受け取り、完全に対称でした。

フロントエンドはポーリングのフォールバックを残します：`EventSource` がエラーになれば自分を閉じ、`tick()` に戻ります。

#### ついでに直した：`pushLines` に重複排除がない

SSE の切断・再接続時にブラウザは元の URL（`after` は不変）を使うため、サーバーは古い行を再度送ります。以前の `pushLines` はそのまま `lines.push()` していたので重複行が出ました。現在は `idx` で重複排除します。

#### ASR をなぜ GPU に載せないのか（評価したが不採用）

翻訳はもともと GPU（vLLM）で動いており、GPU を使うべきはここだけです。ASR は評価に値しますが：

- `sherpa-onnx` の wheel は **CPU のみでビルド**されている（`ldd` で `libcudart`/`libnvinfer` が見つからない）
- `from_sense_voice(provider="cuda")` は**静かにフォールバック**する：`Please compile with -DSHERPA_ONNX_ENABLE_GPU=ON. Available providers: CPUExecutionProvider. Fallback to cpu!`
- `provider="trt"` は即座に拒否：`Tensorrt support for Online models only`

GPU 化するには sherpa-onnx を自分で再ビルドする（CUDA 13.2 に合う onnxruntime が必要で、**その wheel は存在しない**。4.8 参照）か、rec と同様に fbank + CTC の TRT 推論を自作するしかありません。**しかも ASR は 147ms しか占めておらず、利得の上限はこの 147ms** —— ストリーミングで節約した 600ms と比べてまったく割に合いません。

**結論：GPU はすでに正しい場所で使われている。** 字幕チェーンの次の一銭は ASR の速度ではなく精度に使うべきです。

### 4.16 文分割：「固定 3 秒で切る」から「自然なポーズで切る」へ（2026-11-21）

**問題**：ユーザーは字幕を見て「3 秒ごとに強制的に切られている」と感じました。コードを調べると実際はずっと自然なポーズ駆動でした —— `--hold 0.42` が無音を判定し、`--max-s 3.0` は最終手段の上限にすぎません。しかし**実測はユーザーの感覚が正しいことを示しました**：

62 秒の実会議音声（`pw-record` でキャプチャカードから直録）をオフラインで区間分割し、129 区間を統計：

| パラメータ組 | 区間数 | 無音切れ | 上限到達 | 区間長の中央値 | p75 |
|---|---|---|---|---|---|
| max=3.0 hold=0.42（改修前） | 25 | **44%** | **56%** | 2.54s | 2.86s |
| max=4.0 | 19 | 68% | 32% | 3.22s | 3.62s |
| max=4.5 | 19 | 74% | 26% | 2.92s | 4.20s |
| max=5.0 | 17 | 76% | 24% | 3.08s | 4.72s |
| max=6.0 | 15 | 80% | 20% | 3.86s | 5.78s |
| max=8.0 | 15 | **100%** | **0%** | 3.20s | 5.84s |

**56% の区間が上限到達による強制切断** —— つまり「固定 3 秒」は文字通り半分以上成立していました。

**根本原因は「時間を使っていること」ではなく、「ポーズのしきい値が 0.42s の一つだけであること」**：ニュース読みの語間の小さなポーズはしばしば 0.3~0.4s に達し、ちょうど切断を発火させるので半文で切れます。一方、一文を本当に話し終えたときの長いポーズ（0.6~1.2s）はまだ現れず、3 秒の上限が先に来ます。二つのしきい値を固定すると、どちらも裏目に出ます。

**改法：しきい値を区間長で階層化し、最終手段の上限を緩める。**

```
有声 < seg_mid(1.2s)  → hold_long(0.90s) の長いポーズを待つ   # 次の文とつなげる、細切れにしない
有声 < seg_long(2.4s) → 基準の hold(0.45s) を使う
有声 ≥ seg_long(2.4s) → hold_short(0.30s) で切る              # すでに十分長い、遅延を増やさない
max_s = 6.0                                                   # 最終手段
```

#### 踏んだ罠：「無音切れの比率」を判断基準にすると結論が誤る

その指標で見ると、`max_s 7.0 + hold_short 0.25 + seg_long 1.8` は **無音切れ 100%、p75 は 3.88s** を達成し、完璧に見えます。しかし実際の音声で聞くと、ASR テキストは**4.5 案より細切れ**でした：

| 4.5 案（無音切れ 74%） | 7.0 + 0.25/1.8（無音切れ 100%） |
|---|---|
| 所以去**扯**什么台湾会不会进行交易筹码？ | 所以去**者**什么，台湾会不会进行交易筹码？ |
| 了不起在中美会晤中国大陆**再讲一下**。 | 了不起在中美会晤。＋做好到路再讲一下啊 |

理由は明快です。0.25 秒のポーズは口頭発話ではほとんどが**語間の息継ぎ**で、そこで切れば半文になります。**「上限に達していない」と「良い位置で切れている」は別のこと**であり、無音切れの比率は前者しか測っていません。本当の判断基準は ASR テキストが読んで完全かどうかだけで、それは人間が確認するしかありません。

#### 上限を 6.0 にしたのも同じ理由（同じ音声を `--wav` で比較）

| max_s | 中央値 | p75 | テキスト |
|---|---|---|---|
| 4.5 | 2.92s | 4.20s | 「有开了等一长会又拍了开了我会」；「大会」が「大」+「会议」に分割 |
| 5.5 | 3.86s | 4.72s | まだ二箇所で文が割れる：「…我会嗯。」+「之后才有亚尔达会议。」 |
| **6.0** | 3.86s | 5.78s | 「了不起在中美会晤中国大陆再讲一下啊，我认为就是这样了」が一文に統合 |
| 7.0 | 3.86s | 5.78s | **ハルシネーション発生**：同じ箇所の「等一长会议」が「德拉兰会议」に |

7.0 の行が最も重要な否定証拠です：**区間が長すぎると ASR が作り話を始めるのであり、長ければ長いほど良いわけではありません**。6.0 がテキスト品質の最適点です。

**効果：ASR 原文の完全性が明らかに向上**（同じ音声を `--wav` でオフライン実行）：

| 改修前（3s） | 改修後（6s 階層化） |
|---|---|
| 「这个都没有啊，怎么可能第一次。」+「结论那不可能的事嘛啊。」 | 「这个都没有啊，怎么可能第一次就有结论，那不可能的事。」 |
| 「呃，三强会物三强的峰会我。」+「不认为。」 | 「三角的峰会我不认为。」（「我不认为」が分割されなくなった） |
| 「所以去什麼台不会行交易？」 | 「所以去扯什么台湾会不会进行交易筹码？」 |
| 「了不起在中美会晤中国大陆在。」+「一下啊，我认为就是这样了。」 | 「了不起在中美会晤中国大陆再讲一下啊，我认为就是这样了。」 |

3 行目が最も雄弁です：区間が短すぎると ASR は文脈を聞き取れず、「什么台不会行交易」は文字化けになります。区間を一文が完結する長さまで伸ばすと、「什么台湾会不会进行交易筹码」と認識されます。**文分割の誤り → ASR の誤り → 翻訳はさらに誤る**、この連鎖はつながっています。

**コスト**：文字出し遅延の中央値が 2.54→3.86s、p75 が 2.86→5.78s（オフライン 62s サンプル）。オンライン実測の中央値は 4.1s。これは「文が完全になる」ことと引き換えで、`--max-s 4.5` に戻せば中間状態に戻せます。

**ついでに直した**：`--min-s 0.25` は純ノイズ区間を通してしまい、SenseVoice が `" 。"` を返すとページには空の字幕行が出て、翻訳も一回むだに消費します。現在は `recognize()` が `SUBSTANCE` 正規表現で実質文字（中日韓文/仮名/英数）を選別し、句読点だけなら破棄します。

**自分で調整する方法**：`tools/seg_ab.py` は Segmenter だけを実行し（ASR/翻訳に触れない）、数秒で結果が出ます。`--sets` に任意のパラメータ組を渡せます：

```bash
./asr-venv/bin/python tools/seg_ab.py /tmp/meet60.wav
./asr-venv/bin/python tools/seg_ab.py /tmp/meet60.wav --sets "4.5:0.45:0.30:0.90,6.0:0.45:0.30:0.90"
```

判断は**無音切れの比率**（高いほど自然なポーズで切れている）と **p75 区間長**（文字出し遅延の裾に直接相当）を見ます。

**未解決のこと**：エネルギー法では「語間のポーズ」と「文間のポーズ」を区別できず、長さで推測するしかありません。本当の文境界にはイントネーションの下降や句読点レベルの意味モデルが必要で、エネルギーしきい値では不可能です。現在も 26% の区間は強制切断で、`soft-cut` の後退探索でエネルギーの谷を探して受け止めています。

#### ただし「自然なポーズ」自体に物理的な上限がある

`tools/pause_hist.py` で同じ 62 秒音声のポーズ分布を測りました（しきい値の口径は Segmenter と同一）：

```
ポーズ総数 59   総時間 17.3s / 62.0s
≥0.20s  35 個 59%
≥0.30s  26 個 44%
≥0.45s  17 個 29%
≥0.60s  10 個 17%
≥0.90s   0 個  0%     ← 一つもない
```

**中国語の口頭発話には 0.9 秒以上のポーズが存在しません。** 最も長い箇所でも 0.8 秒強です（0.8s の档に 4 個）。したがって：

- `--hold-long 0.9` は実コーパスでは**ほとんど決して満たされません**。その役割は「長いポーズで頻繁に切る」ことではなく、**一文の冒頭を 0.5 秒の断片に切らないようにする**ことです —— 短い区間はむしろ待ち、`--seg-mid` に達して 0.45 のしきい値に切り替わるまで待ちます。
- 実際に区間を長くしているのは `--max-s 3.0 → 4.5` で、階層化しきい値ではありません。階層化が解決するのは「細切れにしない」こと、上限緩和が解決するのは「強制切断しない」ことです。
- 重要な推論：**区間長 4 秒でも上限に達するのは、パラメータ調整の失敗ではなく、その文自体が 5~6 秒あるから**です。上限をさらに上げても、より長い待ち時間と引き換えになるだけです。

**本当に解決するには「一段落話し終わるのを待つ」という前提を捨てる必要があります**：ストリーミング ASR（sherpa-onnx の online モデル。`provider="trt"` が online モデルしかサポートしないのが傍証）で話しながら文字を出せば、遅延は区間長から切り離され、文分割は翻訳の文境界を切るためだけに使えます。代償は、ストリーミングモデルの中国語精度が一般に SenseVoice のようなオフラインの非ストリーミングモデルより劣ることなので、実測してから決めます。

### 4.17 訳文が「純粋な目標言語」を守れない：prompt の書き直し + 残留検出（2026-11-21）

**症状**：中日相互翻訳で 7B が原文を大量にそのまま写します。実測で捕まえた出力：

```
原文 我是主持人谭英文      → 我是主持人田英和      （文全体が中国語のまま、翻訳になっていない）
原文 深zのアプリで何点给…  → 在深Z的应用中给深Z评分多少
原文 …中国大陆再讲一下啊，我认为就是这样了。
     → 了 pesticid在中国と米国の会見で…私はこれが正しいと认为。
原文 因为他的很容易跟韩国做对比是。
     → Because it is easy for him to compare with South Korea.   （文全体が英語に）
```

**旧 prompt が守れない理由**：「訳文は純粋な中国語/純粋な日本語でなければならず、原文の語を一つも残してはならない」とだけ書いており、すべて抽象的な規則で反例がありません。しかも**中日が漢字を共有する**という特殊性により、モデルには「正しく見える」手抜きの余地が大量にあります —— 中国語をそのまま日本語として出力しても、一文字一文字が合法な漢字なので、モデルには直す動機がありません。

**変更**（`_tr_system()`。ついでに `translate` と `translate_stream` に完全重複していた二つの prompt を統合）：

1. **まず誤りを訂正してから翻訳**：文脈に応じて同音の誤字を直すことをモデルに明示的に許可する（`科意`→`刻意`、`三强贵物`→`三强会晤`）。言わなければ誤字を忠実に翻訳します。
2. **実例の反例を与える**：実測で捕まえた悪い出力を反面教師にする方が抽象的な規則より効きます —— 7B の模倣傾向は規則遵守よりはるかに強い。
3. **訳後に自己検査を要求**：「残留した仮名/中国語文法があれば文全体を書き直す」と名指しする。

**実測比較**（`tools/tr_quality.py`、14 条の実用例、同一の vLLM）：

| 原文 | 旧 prompt | 新 prompt |
|---|---|---|
| 我是主持人谭英文 | 我是主持人田英和 ← 丸写し | 私は司会の谭英文です |
| 深zのアプリで何点给深zに評価するか | 在深Z的应用中给深Z评分多少 | 该怎么评价深z这款应用？ |
| 中方刻意给韩国好处 | 中国は韓国に特別な利益を与えた | 中国側は意図的に韓国に便宜を図った。 |
| 中方科意、韓国に良いところを与える | 中方希望给韩国好的印象 ← 誤字を訂正せず | 中方有意给予韩国一些好处。 |
| 身体面にアメリカは坚持するべきです | 美国在身体方面应该坚持 ← 「坚持」を丸写し | 在美国方面，美国应当坚持立场。 |

**ただし長文では依然として漏れます**：`…之后才有`（「才有」が残る）、`…交易筹码`（「筹码」が残る）、`…我认为就是这样了`（「认为」が残る）。この部分は直っておらず、原因は後述。

#### 残留検出 + 一度だけの再試行を追加したが、長文にはほぼ無効

`lang_clean()` の二つの判定：
- **日→中の翻訳では仮名を検査** —— 誤検出ゼロで信頼できる。
- **中→日の翻訳では簡体字専用の字形**（`给/这/说/对/时/个`…、日本語では繁体字や別字形を使う）+ **文全体に仮名がなく 6 文字以上**（一文の長さの日本語に助詞の仮名がないことはあり得ない）。

汚れを検出したら強化指示を付けて一度だけ再試行し、それでも汚れていれば初版を保持します（半文で言語が混ざっていても空白よりましで、無限に再試行して翻訳スレッドを止めるわけにはいきません）。カウントは `/api/status` の `tr.retry / tr.fixed`。

**盲点（実用例 14 条で、汚れた訳文を一つも検出できず）**：「才有」「筹码」「认为」はすべて**中日同形語**で、日本語でもそのまま書けるため、文字のレベルでは検出できません。正確に検出するには「訳文が原文の 2 文字以上の断片を含むか + 同形語のホワイトリスト」しかなく、ホワイトリストは極めて脆く、誤検出の代償は毎文ごとに翻訳をもう一度走らせることです。

**結論：これは 7B の能力上限であり、prompt の書き方が悪いのではありません。** 「文全体の丸写し」という最も明白な誤りでさえ、prompt を変えて 50% から 20% 程度に下がっただけです。本当に解決するにはモデルを替える必要があります：このマシンには `qwen3627b`（19G）、`Qwen3.8-27B`（16G）、`qwen35a3b`（35B-A3B MoE、23G）があります。**MoE のものが最適** —— 活性パラメータが 3B だけで、速度は 7B に近く、品質は 35B に近い。ただし現在 vLLM がすでに 34G/61G を占めており、新規インスタンスには 26G の余裕しかありません。停止時間の窓を取って切り替える必要があり、しかも音声アシスタント（8095 も同じ `qwen` を使う）に同時に影響します。

### 4.18 35B-A3B への A/B：品質は勝ち、遅延は負け（2026-11-21）

前節で「7B は純粋な目標言語を守れない」を能力上限に帰したため、サービスを止めてモデル交換を実測しました。**3 アームを同じ日に走らせ**、同じ 14 文（実測の悪例 10 条を含む）+ 62 秒の実音声を使っています。

| アーム | ランタイム | モデル | 初回トークン中央値 | 全文中央値 | 既知の残留 |
|---|---|---|---|---|---|
| **A** | vLLM | Qwen2.5-7B-AWQ | **88ms** | **571ms** | 7 箇所（`才有`/`筹码`/`SUCH`/`pesticid`/`认为`/英文の文） |
| **B** | SGLang 0.6.0 | Qwen3.5-35B-A3B GPTQ-Int4 | 419ms | 933ms | **0 箇所** |
| **C** | vLLM | Qwen3.5-35B-A3B w4a16 | 400ms | 2300ms | 未測定（同モデル） |

**B の品質は本当に一変しました**。既知の 7 箇所の失敗が一度にすべて消えています：

| 原文 | A（7B） | B（35B-A3B） |
|---|---|---|
| 这就投扯太远的了… | ここでは **SUCH** 問題を提起する可能性は低い | そもそもこのような場で提案されることはあり得ません |
| 了不起在中美会晤…我认为就是这样了 | **了 pesticid**在中国と米国の会見で…と**认为** | せいぜい米中首脳会談で中国側が改めて触れる程度でしょう |
| 因为他的很容易跟韩国做对比是 | **Because it is easy for him to compare with South Korea.** | それは韓国との対比が容易だからです |
| Love冷落日本 | 日本の愛は冷たくなった | アメリカが日本を冷遇している |

#### 35B の初回トークンを下げられない理由：プレフィックスキャッシュが当たらない

これが今回最も価値のある発見で、遅延の数字そのものより重要です。

字幕は毎文**同じ 390 文字の system prompt** を使い、7B はプレフィックスキャッシュでこれを無料にしていました（533ms → 94ms）。35B はそれができません：

- **vLLM**：ログが自分で言っています
  `Mamba cache mode is set to 'align' when prefix caching is enabled`
  `Prefix caching in Mamba cache 'align' mode ... support for Mamba layers is experimental`
  `Setting attention block size to 1056 tokens to ensure attention page size >= mamba page size`
  → キャッシュ再利用の粒度が mamba page に押し上げられて **1056 token** になり、こちらの prompt は ~300 token しかないので**永遠にヒットしません**。実測 `Prefix cache hit rate: 0.0%` で、毎文 300 token を prefill し直し、初回トークンが 400ms まで押し上げられます。
- **SGLang**：キャッシュはする（1022ms → 375ms）が、375ms がその下限で、やはり返ってきません。

**つまり遅延は「35B の計算が遅い」のではなく、「毎文 prompt の代金を払い直している」のです。** 推論：どうしても 35B を使うなら、最も効く一手は kernel の調整ではなく、**`_tr_system` を 390 文字から 100 文字程度へ削ること** —— 35B には 7B のような few-shot の例は要りません。この一手はまだ試していません。

#### 三つの罠（いずれも今回踏んだ）

1. **chat template がデフォルトで思考を開く**（`enable_thinking` が未定義だと thinking 分岐に入る）。`max_tokens=200` がすべて思考に焼かれ、`content` は空文字列のまま —— オンラインでは「行間が 9~10 秒、訳文が一文字も出ない」という症状になります。修法：リクエストボディに `chat_template_kwargs: {"enable_thinking": false}` を付ける。`caption_server` には `--llm-think` スイッチを追加済み（デフォルトはオフ）。Qwen2.5 のテンプレートはこの変数を認識しませんが、渡しても無害です。
2. **ファイルに書かれた vLLM コマンドはそのままでは動かない**：`--gpu-memory-utilization 0.9` + `--max-model-len 262144` は 61G の統合メモリ上で OCR/ASR を圧迫して死なせます。`--disable-log-requests` は現在のイメージでは削除済み（そのまま渡すと `unrecognized arguments` で即終了）。
3. **初回リクエストに 50 秒**：MoE kernel の自動チューニング。ログに `Using default MoE kernel config. Performance might be sub-optimal!` が出ます —— `E=256,N=256,device_name=Orin,dtype=int4_w4a16.json` が不足しているため（ファイル内の qwen36b 版コマンドは `/root/.cache` からイメージへコピーします）。スモークテストのタイムアウトは 60 秒に設定しないと、最初の一発が必ず偽の失敗になります。

**この節の結論は後に 4.19 で覆されました：** ランタイム（Magnitude）を変えれば token 粒度のプレフィックスキャッシュが得られ、35B は prompt を変えずに載ります。以下の当時の判断と証拠は残します。「vLLM 上で 35B がなぜ遅いか」の根本原因分析は今も成立するからです。

### 4.19 Magnitude で 35B-A3B をロードする：同じマシンでランタイムを替えるだけで帳尻が合う（2026-11-21）

4.18 の結論は「35B は品質で勝ち、遅延で負ける」で、負けた原因は**プレフィックスキャッシュが得られないこと**でした。それなら kernel を調整するのではなく、ランタイムを替えるべきです —— **Magnitude**（YC S25、Rust 製のローカル推論エンジン、kernel 自動チューニング内蔵、GGUF 路線、OpenAI 互換）へ。

**コマンド一つで差が確定します**：同じ 390 文字の system prompt を連続送信すると、Magnitude は各 chunk に `timings` を付け、直接こう報告します

```
第1発 prompt_n=296 cache_n=0   prompt=1130ms
第2発 prompt_n=1   cache_n=295 prompt=25ms   ← プレフィックスが token 粒度で再利用される
```

`cache_n` は「初回トークンを見る」よりはるかに信頼できます：**何 token が KV プレフィックスキャッシュから再利用されたか**を明示してくれるからです。vLLM 側ではこの数が 0（1056 token の再利用粒度）、Magnitude では 295/296。

#### 5 アームの実測（同じ 14 文、同じ `_tr_system`、同じリクエスト形状）

| アーム | ランタイム | モデル | 初回トークン中央値 | 全文中央値 | 既知の残留 |
|---|---|---|---|---|---|
| A（旧現役） | vLLM | Qwen2.5-7B-AWQ | 88ms | 571ms | 7 箇所 |
| B | SGLang 0.6.0 | 35B-A3B GPTQ | 419ms | 933ms | 0 |
| C | vLLM | 35B-A3B w4a16 | 400ms | 2300ms | 未測定 |
| E9B | Magnitude | Qwen3.5-9B Q4 | 157ms | 929ms | 0 |
| **D（現役）** | **Magnitude** | **Qwen3.5-35B-A3B UD-Q4_K_XL** | **89ms** | **487ms** | **0** |

D アームは**短い文**では A より速く、品質は B と同等。62 秒の実音声 17 行で、A の 7 箇所の残留（`才有`/`筹码`/`SUCH`/`pesticid`/`认为`/英文の文/`日本の愛は冷たくなった`）がすべて消え、残ったのは ASR の誤字 `Love`（「美国」の聞き間違い）を固有名詞として保持した一箇所だけでした。

#### しかしオンラインの初回トークンは ~490ms で、89ms ではない —— この法則は覚えておく必要がある

実際に載せて初めて分かりました：`ttft` の中央値が 490ms。`CAP_DEBUG=1` でサーバーが自報する `timings` を出して初めて見えました：

```
[tr] hdr=531ms ttft=531ms | srv prompt_n=49 cache_n=290 prompt_ms=491
```

キャッシュヒット（`cache_n=290`）は問題なく、遅いのは**新規トークンの prefill**です。測って得られた関係は：

```
TTFT ≈ 25ms + 6~8ms × 新規トークン数
```

- 短い文（8~20 token）→ 90~150ms。だから A/B の 14 文テストは美しく見えた
- **オンラインの実際の区間は 5~6 秒の日本語文（60~80 token）→ 450~700ms**
- さらに `【上文】` の数十 token（毎文変わり、キャッシュに乗らない）が重なる → これが 490ms の出どころ

根本原因は MoE の prefill が**小さなバッチ**に極端に不向きなことです：60 token でも 40 層のほぼすべてのエキスパート重み（22.9G）を読むのに対し、デコード時は活性化する 3B しか読みません。つまり **MoE は「デコードが安く、prefill が高い」、dense はその逆**です。これが vLLM 上の 35B でも初回トークンが同じ 400ms になる理由でもあります —— vLLM のせいではなく、この種のモデルの物理的特性です。

**正味の効果：全文訳了までの時間は 7B と同等（1071ms 対 1085ms）で、初回トークンだけが約 300ms 後ろへずれる。** 字幕が 0.5 秒遅れるのは十分許容できるので、今回は交換しました。

#### 三つの新しい罠

1. **思考を切れないと訳文が飲み込まれる**（4.18 の 1 条目と同じ病）。Qwen3.5 は `chat_template_kwargs: {"enable_thinking": false}` を認識します（切ると reasoning が 640 文字から 0 になり、`content` 18 文字が正常に出る）。しかし **LFM2.5 はこの変数を認識せず**、相変わらず 600 文字超の reasoning を先に吐き、`content` は常に空 —— 最初に LFM で試したときは「Magnitude は思考を切れない」と誤判定しかけました。`reasoning_effort: "none"` は LFM では 400 を返し、Qwen では通ります。
2. **`--ctx-lines 0` が「全文脈を持たせる」になる**：`prev[-self.ctx_lines:]` は 0 のとき `[0:]` と等しく、履歴全体を prompt に詰め込みます（`prompt_n` が 80 から 138 に増え、初回トークンが 300ms 余計にかかる）。`_ctx_before()` で明示的に塞ぎ、単体テストも追加済み。
3. **Magnitude 自身のダウンローダは直結より 3~5 倍遅い**：`catalog pull` は約 10MB/s、同じファイルを `curl` で HF へ直結すると 15MB/s 出て、23GB に 41 分かかりました。重みは `blobs/lfs-sha256-<hash>` 形式で書かれるので、**HF のキャッシュディレクトリを手で作って放り込まないこと**。認識されません。

#### デプロイ形態：現在は 35B のみ（vLLM は停止済み）

35B（27.9G）+ システム ≈ 33G/61G、残り 28G。**vLLM 7B は 2026-11-21 11:53 に停止済み**（`docker stop vllm-qwen`。restart policy は `no` なので自動復帰せず、対応する systemd unit もありません）。コンテナは削除しておらず、ロールバックは `docker start vllm-qwen` だけ。共存期の設定を記録として残します：vLLM を `--gpu-memory-utilization 0.25`（約 15G）に絞る + 35B + システム ≈ 48G/61G。7B の KV プールは元 19.94G/373k token でしたが、実際に使うのは数千程度なので絞っても損失はありません。

```
magnitude-dockerd.service   独立 dockerd（独立 data-root、主 daemon の三つの本番コンテナに触れない）
magnitude.service           コンテナ起動 → /health 待ち → 35B を明示的に load → Ready 待ち（冷起動 ~150s）
caption-bench.service       --llm-base http://127.0.0.1:10100/inference/v1 --llm-model <id> --llm-key <key>
```

二つの unit は enable 済みで、**2026-11-21 11:54 に実際に systemd 管理へ移しました**：手動 dockerd を停止 → `systemctl start magnitude-dockerd` → `systemctl start magnitude`、冷起動 **77 秒**で Ready、二つの業務サービスを接続し直した後、字幕の初回トークン p50 は 474ms、`NRestarts` は増加しなくなりました。`/opt/meeting-copilot` は `/etc/fstab` にあり、`local-fs.target` が dockerd より先なので起動順に問題はありません。

移行手順（そのまま使える）：

```bash

sudo systemctl stop caption-bench voice-bench
# 2 コンテナ停止（data-root はそのまま、コンテナ状態は保持）

# 3 手動 dockerd を停止
sudo pkill -TERM -f 'magnitude-data/daemo[n].json'
# 4 systemd へ引き渡す（dockerd が上がってからモデルを load）
sudo systemctl start magnitude-dockerd && sudo systemctl start magnitude
# 5 業務を接続し直す

```

> ⚠️ **踏んだ罠 1：`pkill -f` が自分自身を殺す**。`pkill -f 'dockerd --config-file .../daemon.json'` と書くと、
> この ssh リモートシェルのコマンドラインにも同じ文字列が含まれるため、`pkill` がシェルごと殺し、`Exit 255` で突然切断されます。
> `daemo[n].json` のような文字クラス表記を使い、正規表現が自分のコマンドラインに一致しないようにします。
>
> ⚠️ **踏んだ罠 2：手動で起動した dockerd があると unit が無限に失敗再起動する**（午前中に累計 **4631 回**リトライ、ログが溢れ、CPU をむだに焼く）。
> 根本原因は `dockerd.pid` がすでに存在し、systemd が毎回 `process with PID xxx is still running` で押し戻され、`Restart=on-failure` が 5 秒ごとに再試行すること。
> `NRestarts` は累計カウントで移行後もゼロに戻らないため、**まだループしているかは、それが増えるか + `ActiveEnterTimestamp` が変わるかでしか判断できません**。

**7B へのロールバック**：`docker start vllm-qwen` → `/v1/models` を待つ（約 66s、初回は 250s のことも）→ `caption-bench` / `voice-bench` の `--llm-*` を `--llm-model qwen` に戻す（base はデフォルト 8000）→ この二つのサービスを再起動。

### 4.20 system prompt を削って初回トークンを 200ms に収めようとした：短縮版の方が遅い（2026-11-21）

4.19 でオンラインの初回トークン 490ms を「新規トークンの prefill」に帰しました。最も手軽な仮説はこうです：`_tr_system` は 390 文字（≈290 token）で、毎文のリクエストで最大の固定テキストブロックだから、~95 文字（≈70 token）まで削れば大きく節約できるはず。

`--tr-prompt short` はそうして追加しました（`_tr_system_short()`。純粋な目標言語 / 同音誤字の訂正 / 半文は半文で訳す、の三つのハードルールだけ残し、例とフィラー規則はすべて削除）。サービスを止めて四つの格を実行した結論は**逆**でした：

| 格 | prompt_n（今回実際に処理） | cache_n（再利用） | 初回 p50 | 初回 p90 | 全文 p50 | <200ms |
|---|---|---|---|---|---|---|
| full/ctx2 | 61 | 290 | 300ms | 345ms | 648ms | 0/24 |
| short/ctx2 | 124 | **0** | 367ms | 416ms | 749ms | 0/24 |
| full/ctx0 | 26 | 290 | 244ms | 264ms | 553ms | 0/24 |
| short/ctx0 | 89 | **0** | 340ms | 615ms | 687ms | 0/24 |

（実際の日本語区間 12 本 × 各格 2 巡、静かなマシン、`tools/ttft_prompt_ab.py`）

**短縮版の `cache_n` は常に 0。** 290 token のプレフィックスは毎文ヒットし、70 token のプレフィックスは一度もヒットしません。その結果、短縮版は system が 220 token 減っていても、prompt 全体（上文を含む）を prefill し直すため、長い版より 60~70ms 余計にかかります。

「プレフィックスが短すぎるとキャッシュできない」わけではありません。同じ prompt を連続送信すれば、両档ともきれいにヒットします：

```
full   第1発 1223ms cache=0/298 → 第2発 72ms cache=297/1
short  第1発  457ms cache=0/92  → 第2発 67ms cache=91/1
```

差が出るのは**ユーザー内容が毎文変わる場合**（オンラインの実際の形）だけです：長いプレフィックスは安定して 290 token を再利用し、短いプレフィックスはゼロになります。機構は調べられていません（Magnitude は非公開）が、挙動は非常に安定しており、24 回のリクエストで 24 回とも 0 でした。**長く使えるなら長く使う —— お金はかかりません。**

#### 初回トークンは 200ms に入らない、これは硬い床

`prompt_n` と初回トークンを並べて見ると、モデルは

```
TTFT ≈ 65ms + 3.5~6.5ms × 新規トークン数
```

- 新規トークン = 1（そのまま再送）→ 72ms
- 新規トークン = 26（上文を削り、本文だけ）→ 244ms
- 新規トークン = 61（現網の形：本文 + 上文二文）→ 300ms

**200ms に入れるには、新規トークンを 20~30 個以内に抑える必要があり**、つまり 15 文字前後の一文で、上文も付けないこと。実際の会議の一区間は 5~6 秒、60~80 文字なので、物理的に届きません。したがって「初回トークン 200ms」という目標は捨て、別のものを見るべきです：

- まだ下げられるのは上文だけ：`ctx0` で 56ms 節約（300→244）できますが、代償は品質の崩壊（`だ。` → `的。`、独立した半文が主語を失うとゴミ翻訳になる）—— 割に合わない
- ~~オンライン 490ms とオフライン 300ms の差 190ms はスケジューリングの問題~~ → **4.21 が否定**：その 190ms は「オンラインの文がより長く、上文もより長い」だけで、token に換算すればオンラインとオフラインは完全に一致する（65ms + 4.5~6.7ms/token）

**落としどころ**：`--tr-prompt` のデフォルトは依然 `full`。短縮版は dense モデル用にコードへ残します —— dense の prefill は token に対して線形に課金されるので、「prompt を削る」道は 9B/7B では成立し、MoE では成立しません。

### 4.21 ctx-lines を 1 に（-90ms）、workers を 1 に（差なし）、9B は長文で 35B に敗北（2026-11-21 午前）

**まずフィールドの意味を確定します**（一度書き間違え、以後のすべての導出が狂いました）：Magnitude の `prompt_n` は**今回実際に処理した token 数**、`cache_n` は**KV プレフィックスから再利用した数**で、両者を足したものが prompt 全体の長さです。したがって「新規トークン = prompt_n − cache_n」は誤りで、**新規トークンは `prompt_n` そのもの**です。

#### 1. `--ctx-lines 2 → 1`：実測の節約は ~90ms で、200ms ではない

オンラインで `Environment=CAP_DEBUG=1` を有効にし、エンジンが自報する `prompt_ms` を直接読む。同じニュースストリームで前後それぞれ一巡（48 対 52 条）：

| 設定 | 新規トークン p50 | エンジン prompt_ms p50 | 初回 p50 | 初回 p90 |
|---|---|---|---|---|
| `--ctx-lines 1` | 53 | 403ms | **435ms** | 811ms |
| `--ctx-lines 2` | 73 | 485ms | **524ms** | 761ms |

20 token 減で 89ms の節約 ⇒ **傾きは約 4.5ms/token**。6.7ms/token で見積もった「上文を一句削れば 200ms 節約」は楽観的すぎました：本当に 200ms 節約するには、前の文が 45 文字以上必要です。短い文のニュース（前の文が 20 文字前後）では 90ms のオーダーになります。

#### 2. `--tr-workers 1 vs 2`：差はない

ctx1 で workers=1 → 435ms、workers=2 → 475ms ですが、二巡の `prompt_n` も異なります（53 対 61、ニュース内容が変わった）。4.5ms/token で正規化すると**両者は等しい**。GGUF エンジンは worker 数で初回トークンを下げません。全期間 `q_tr=0`、`lag≈300ms` で、翻訳スレッドは 1 本で足ります。最終版は 1（待ち行列が一段減る）。

#### 3. 62 秒の実音声で 9B 対 35B の正面比較（`tools/wav_seg_ab.py`）

実際の 16 区間、同じ ASR テキスト、同じ上文、ctx-lines 1：

| アーム | 初回 p50 | 初回 p90 | 全文 p50 | 致命傷 |
|---|---|---|---|---|
| **35B（現役）** | **293ms** | 407ms | **693ms** | — |
| 9B | 326ms | 378ms | 1085ms | 6 文目が 5 文目の訳文をそのまま繰り返す |

9B は**二つの指標とも負け**、全文は 56% 遅く、しかも復読ハルシネーションが出ます。以前 9B の美しい 157ms は短い文（8~20 token）が与えたもので、長い文では「dense の prefill が安い」は実現しませんでした（デコードも遅い）。**35B を残し、9B の線は閉じてよい。**

> ここでの 35B 初回トークン 293ms は caption-bench 停止時に測ったもの。オンラインの同パラメータでは 435ms。差の 140ms は収音 / ASR / 草稿スレッドが CPU を奪っているためで、エンジンのせいではありません —— 「オフラインは良い、オンラインは悪い」は誰が奪っているかを見るべきで、モデルを疑うべきではありません。

**品質は落ちていません**：ctx2 と ctx1 の同じ 16 文を逐文比較すると、5 文は完全に同一、11 箇所の差はすべて同義置換（`凝縮`→`必要となる`、`対比`→`比較`）で、意味の漂流も言語の脱落もありません。`Love冷落日本` の文は両档とも主体を誤って埋めており（ASR が「美国」を `Love` と聞き間違い）、ctx とは無関係です。

**落としどころ**：`caption-bench` は `--tr-workers 1 --ctx-lines 1` で確定。`CAP_DEBUG` は採取後すぐに切る（一行一レコードで、一日中つけていると数十 MB）。

### 4.22 音声アシスタントも 35B-A3B へ（2026-11-21 正午）

**交換前が 7B だった理由**：選んだのではなく、歴史的な順序です。`voice-bench` は当初音声対話だけを担当し、当時マシンには vLLM の Qwen2.5-7B-AWQ（8000 ポート）しかありませんでした。その後字幕もまず 8000 に接続し、4.19 で Magnitude の 35B に替えました。音声アシスタントは 7B のまま誰も触らずに残っていたのです。交換を本当に止めていたのは、**当時未検証だった二つの懸念**でした：MoE の prefill が高い（初回トークンが遅くなるのでは）、GGUF エンジンは単一スロットしかない（二つのサービスが順番待ちになるのでは）。

#### 1. 四つの実シナリオを一通り測る（`tools/voice_llm_ab.py`）

音声アシスタントと字幕では負荷の形がまったく違います：字幕は system が長く（290 token、キャッシュヒット）+ 内容が短く + 出力も短い。アシスタントは system が短く + **数百文字の OCR を伴い得る** + 出力が長い（160 token）。したがって字幕の結論はそのまま流用できません。

`reply-lang=zh`、各シナリオ 3 回、**毎回問い文を変える**（同じ文を繰り返すと prompt 全体がキャッシュに当たり、`prompt_n` が 1 まで落ちて初回トークンが 78ms という偽の値になる）：

| シナリオ | 7B 初回 | 7B 全文 | 35B 初回 | 35B 全文 |
|---|---|---|---|---|
| chat-short（純粋な Q&A） | 98ms | 461ms | 272ms | 887ms |
| chat-multi（3 ターン履歴付き） | 104ms | 1070ms | 426ms | 905ms |
| ocr-mid（画面 ~100 文字） | 102ms | 1899ms | 314ms | **1488ms** |
| ocr-long（画面に一段の口播稿） | 102ms | 2925ms | 472ms | **2127ms** |

- **初回トークンは 170~370ms 遅い**（固定コスト：35B はウォームアップすべき重みが多い）が、**長い回答の全文は 25~35% 速い** —— MoE のデコードは 3B しか活性化しないのに対し、7B dense は毎 token でモデル全体を走らせます。
- 体感遅延 = 初回トークン + 初回文の合成。45 文字程度の初回文で、35B が約 1.2s、7B が約 0.95s。250ms の差は聞き分けられますが、その代わりに次が得られます。
- **品質の差は圧倒的**：7B は「日本語 system + 中国語回答」で `会議的时间确认 needed。`（中日混在）、`優先度が一番高いのは…-topic1-と判断します`（ゴミ token）、`necesita дополнительной информации`（スペイン語）を出します。35B は 12 条のうち一箇所もありません。

#### 2. 並行性は問題にならない（交換前の懸念を覆す）

`magnitude serve --help` には `-h` しかなく、単一スロットに見えます。実測：一方でアシスタントに ocr-long の長出力を繰り返させ、もう一方で字幕の短いリクエストを打つと、**字幕の初回トークンは 204ms から 233ms に上がっただけ（+29ms）**。エンジンは並行スケジュールでき、二つのサービスが 10100 を共有しても順番待ちになりません。オンラインの字幕初回トークン p50 は 435~474ms を維持し、`q_tr=0`、`dropped=0`。

#### 3. つまずいた罠：言語指示をどこに付けるかは、何を書くかより重要

音声アシスタントの価値は「日本語の会議で中国語で読み上げる」こと（`--reply-lang zh`）。ところが 35B に替えた後、**12 条の回答がすべて日本語（0/12）**、7B は 8/12 でした。`tools/voice_lang_fix.py` で四つの書き方、二つのシナリオ × 3 回：

| 書き方 | 35B の中国語率 | 7B の中国語率 |
|---|---|---|
| 指示を system 末尾に（**元の実装**） | **0/6** | 3/6 |
| 指示を user メッセージ末尾に | **6/6** | 6/6 |
| system 冒頭にハード宣言を追加 | 0/6 | 5/6 |
| user 末尾 + system 冒頭の両方 | 5/6 | 6/6 |

user 末尾に置いた瞬間に直りました —— **指示は生成位置に貼り付ける必要があります**。35B では特に顕著で、モデルは「文脈を理解しすぎる」ため、ユーザーが日本語で話し画面も日本語なら、遠くにある中国語の指示を無視します。7B は最後の一文に機械的に従うだけでした。

しかし user に付けるだけでは足りません：system を「純対話版」（画面規則を削除）に分割すると、system が**全面日本語で中国語が一文字もなくなり**、言語指示がまた押し戻されます（3/3 すべて日本語）。そこで最終的な方法は**両方に付ける**こと：system 末尾に一つ + user 末尾に一つ。変更後は 4/4 すべて中国語。

#### 4. ついでに 35B 特有の悪癖を一つ直した

`look` を渡していない（画面を見ていない）とき、35B は「屏幕文字中没有显示今天的会议时间」と答えます —— そのターンはフレームを取っていないのに、責任逃れのように聞こえます。「[屏幕文字] がないときは画面に触れるな」という**否定指示では抑えられません**（2/2 で同じ）。

根本原因は system に「[屏幕文字]」という語が繰り返し現れるため、モデルがそれを引用することです。最終的には**動的 system** に変更：`voice_server.Llm` を `system_core`（純対話）と `system + screen_rule`（画面規則付き）に分け、`stream()` で `"[屏幕文字]" in text` により二択。**その語を与えなければ、問題は消えます。**

#### 5. 変更とロールバック

- `voice_server.py`：`Llm(api_key, think)`（Magnitude は Bearer が必要、Qwen3.5 は思考を切る必要がある）、`available()` に認証ヘッダ、`system_core`/`screen_rule` の動的 system、言語指示の二重付与、`--llm-key` / `--llm-think` を追加
- `deploy/voice-bench.service`：`--llm-base .../10100/inference/v1` + 35B の model id + key
- 新ツール：`tools/voice_llm_ab.py`（四シナリオのマルチアーム比較 + `--concurrent` 横取りテスト + 言語遵守の統計）、`tools/voice_lang_fix.py`（四つの指示書き方の対照）
- **ロールバック**：`docker start vllm-qwen` → unit の三行の `--llm-*` を `--llm-model qwen` に戻す（base はデフォルト 8000）→ voice-bench を再起動。**vLLM コンテナは 11:53 に停止済み**（空転で 15G を占有）だが削除はしておらず、ロールバックは上記二段階で行う。

### 4.23 「次の文が来ると、前の文の行が丸ごと消える」：全量再描画によるスクロールアンカーの漂流（2026-11-21 正午）

**現象**（ユーザー報告）：前の文が長文で訳文がまだ逐字で流れているところに次の文が来ると、前の文の**行全体（原文+訳文）が見えなくなる**。しかも長い文でだけ顕著。

#### 1. まずデータの問題でないことを証明する

独立した二つの証拠を、いずれもオンラインで取りました：

- `tools/sse_regress.py` が `/api/events` を 120 秒購読：**407 イベント、206 行、後退 0 回、空化 0 回**。各 seq の訳文は厳密なプレフィックス成長。
- `/api/status` の `tr: {retry: 1, fixed: 0}`：219 区間のうち「残留検出 → 同期再翻訳」が発火したのは 1 回だけで、しかも救えていない（`fixed=0` なら行全体の置換は起きない）。したがって再翻訳が長文を差し替えたのではありません。

サーバー側にも `trans` をクリアする経路は実際に存在しません（`cap.clear()` だけがあり、それは `/api/control` の「クリア」ボタンにしか繋がっていません）。`cap.lines` は `deque(maxlen=400)` で、現在の 219 行は上限に達していません。

#### 2. 根本原因：`innerHTML` による全量再構築 + ピクセル値 `scrollY` の書き戻し

旧 `render()` はプッシュを受け取るたび（ストリーミング時は約 80ms ごと）にこれを実行していました：

```js
const y = window.scrollY;
const atBottom = (window.innerHeight + y + 80) >= document.body.scrollHeight;
m.innerHTML = lines.slice(-30).map(...)   // 30 行を丸ごと再構築
window.scrollTo(0, atBottom ? document.body.scrollHeight : y);
```

長い文の訳文が逐字で高さを増しており、再構築後の `#main` の**総高さは変わるのに `y` は同じピクセル値のまま** —— 同じ `y` が指すのはすでに別の内容で、ユーザーが読んでいる行がビューポートの外へ押し出されます。文が長いほど高さの変化が大きく、だから長い文でだけ顕著でした。さらに 80ms ごとに 30 行の DOM を再構築するので、ブラウザはツリー全体を再レイアウトし、フレーム落ちがこの見え方を増幅します。

**これは「データが削除された」のではなく「ビューポートのアンカーが漂流した」** —— だからページを更新するか少し上へスクロールすると、その行は実際には残っています。「内容が消える」バグがどちらの種類か判断するには、まずこれを見ます：データ層で後退が再現すればバックエンド、再現しなければレンダリングです。

#### 3. 修法：増分レンダリングへ変更

行ごとに**常駐する DOM ノード**（`dom: seq -> {root, head, o, tr}`）を持ち、毎回変わるテキストノードだけを書きます：

- 訳文がストリーミングで伸びるとき、**伸びるのは現在の行のテキストノードだけ**で、上の 29 行は一文字も触らず、幾何位置も動かない
- 新しい行は `appendChild` で追加。順序の入れ替えは実際に順序が崩れたときだけ（`appendChild` は既存ノードに対しては「移動」で、再構築も内容の喪失もしない）
- スクロールは「本当に新しい行が来た」かつ「もともと最下部にいた」ときだけ実行。**訳文が元の行の中で伸びてもスクロールしない** —— ここが視線を押しのけていた箇所
- 草稿行も常駐ノードで、`draft` が空なら `remove()`。文字列の結合はしない

#### 4. 検証方法：ページの JS を抽出し DOM mock で走らせる

`tools/dom_render_test.js`：`caption_server.py` から `<script>` を抽出し、極小の DOM（`createElement` / `appendChild` / `remove` / `querySelector` / `nextElementSibling`）を注入して、文字列だけでなく**ノードの同一性**を直接アサートします：

- 長い文を 20 回ストリーミングした後、30 行目の DOM ノードは**同じオブジェクトのまま**（`===`）で、テキストは一文字も変わらない
- 新しい行が来ても、前の行のノードは再構築されず、前の文の訳文が完全に残る
- 上下二文が交錯してプッシュされても互いを踏まず、`final` 後も訳文が残りカーソルのクラス名が消える
- 草稿行の挿入/削除が既存行に影響せず、クリアで「翻訳を待機…」に戻る

18 項目すべて通過。**しかも Jetson 上でオンラインの `caption_server.py` から JS を再抽出して実行** —— 検証したのはローカルの複製ではなく、オンラインのファイルです：

```bash
python3 -c "import re,pathlib;s=pathlib.Path('caption_server.py').read_text();\
pathlib.Path('tools/_page_check.js').write_text(re.search(r'<script>(.*?)</script>',s,re.S).group(1))"
node tools/dom_render_test.js
```

> 罠：ページの JS を変更したら必ず `tools/_page_check.js` を再抽出すること。そうしないと古いコードをテストします。ローカルのスクリプトが sha1 を比較して不一致を警告します。

**コスト**：今回の変更はフロントエンドだけですが、`PAGE` はモジュールレベルの定数なので**caption-bench を再起動しないと有効になりません**。再起動すると蓄積済みの行は消えます。

### 4.24 字幕を「最新が最上、古い行は下へ流れる」に変更（2026-11-21 午後）

ユーザーの要求：最新の一条を最上部に表示し、新しい文字が出たら画面全体を下へ押し出す。2026-11-21 正午の版は「下部に追加 + 最下部へスクロール」でした。

変更はページのレンダリング層のみ（`caption_server.py` の `PAGE`）：

| 箇所 | 旧（下部に追加） | 新（最新が最上） |
|---|---|---|
| `syncLine()` のノード生成 | `appendChild` | `insertBefore(node, firstElementChild)` |
| `syncDraft()` | 末尾に付ける | 先頭に付ける（草稿が最新の一条） |
| 順序検証 | seq 昇順 | `orderOk()`：草稿が先頭、残りは **seq の降順** |
| 回収 | スクロール時に最も古いものを削除 | 同じ。ただしそれが今は**最下部**にある |
| スクロール | 最下部にいれば `scrollTo(bottom)` | **最上部にいれば何もしない**（新しい行の挿入が自然に内容を下へ押す）。下へスクロールしているときは補正しないと押しのけられる。後述 |

**スクロールアンカーも一緒に反転させる**必要があります。そうしないと 4.23 のバグを逆向きに再発させます：

- 最上部（`scrollY <= 24`）：何もしない。新しい行が先頭に挿入される → 内容が画面全体で下へずれる。これが「下へ流れる」という見え方。
- 下へスクロールして古い行を見ている：挿入前の最初の一条を基準に固定し、挿入後に `getBoundingClientRect().top` の**差分**で `scrollBy` を補正する。
  向きを間違えやすい：内容が `h` ピクセル押し下げられると `top` は `h` だけ**大きくなる**ので、`scrollBy(0, +h)`（余分に `h` スクロールする）と書く。
  `anchorTop - topNow` と書くとスクロールが逆方向になり、視線がさらに大きく跳ぶ。
- `#main` に `overflow-anchor:none` を追加：Chrome 標準のスクロールアンカリングが先頭挿入時に `scrollY` をこっそり変え、手計算の補正と重なると漂流する。

テスト `tools/dom_render_test.js` も 26 項目に変更し、追加した主要なもの：

```
[ok] 最新的一条在最上（35） / 最老的一条沉到底部（6）
[ok] 新行插到最上，原来的 35 退到第二位
[ok] 草稿行在最上 / 草稿移除后 36 回到最上
[ok] 新行把上面的内容往下推了 100px
[ok] 滚动补偿到位，scrollY=400（期望 400）
[ok] 贴顶时不做补偿，新行自然把内容往下推
```

DOM mock にはそのために `insertBefore` / `getBoundingClientRect`（「何番目の子 × 100px」でレイアウトを模擬）と `window.scrollBy` を追加。これも**Jetson 上でオンラインファイルから再抽出して実行**し、26 項目すべて通過。バックエンドの `test_caption_pipe.py` も 14 組すべて通過。

> 注意：この順序は「逆順」です。将来また下へ続けて話し、順方向に読ませたくなったら、上の四箇所を戻すだけ（要点は `orderOk` の走査方向とスクロールアンカーを一緒に変えること）。

### 4.25 画面上の文字で ASR の固有名詞を訂正する：必要時だけ提示し、全量注入はしない（2026-11-21 午後）

要件：「画面を見ながら字幕を出すとき、画面上の文字で誤りを直す」。できますが、**画面テキストを丸ごと翻訳リクエストに詰め込んではいけません** —— 実測では負の効果です。

#### まずコストと効果を測る（`tools/screen_hint_ab.py`、実際の 6 区間 × 3 アーム）
| アーム | 画面文字数 | 初回 p50 | prompt_n | prompt_ms |
|---|---|---|---|---|
| none | 0 | 87ms\* | 1 | 25 |
| h60 | 113 | 423ms | 134 | 352 |
| h120 | 176 | 417ms | 160 | 361 |

\* none のアームは、オンラインで直前に同じ文を訳していたため prompt 全体がキャッシュに当たり（`cache_n=351`）、速すぎて信頼できません。ctx1 の現網の形で換算すると、113 文字 ≈ +72 token ≈ **+250~320ms/文**。

**さらに致命的なのは効果**：h60 では五文のうち三文が悪化 —— 「三社の会談」が「这三家公司的首次会谈」と訳され、「この後ちょっと…」から「这位先生在这三家公司此次会谈中」が勝手に湧き、「特朗普那边则是特朗普那边的情况」が繰り返されました。根本原因は二つ：
1. キャプチャカードはプレゼンターの画面全体を撮っており、**そこに自分たちの字幕ページが開いている**ので、画面テキストには前の文の中国語訳が含まれる → 訳文を参考としてフィードバックし、自己循環する。
2. 画面の下三分の一、タイトルバー、メール一覧などの文字は本文と無関係だが、モデルはそれに「合わせよう」とする。

#### したがって「ヒットしたときだけ提示する」だけを実装
`ScreenHints`（`caption_server.py`）：
- バックグラウンドで 15 秒ごとに voice-bench の `/api/look` へ OCR を要求（**字幕サービスは `/dev/video0` に触れない**。あのデバイスは排他で、voice-bench が常駐保持している。内部で画面フィンガープリントによりキャッシュし、同一画面は約 0.5s、新しい画面は約 1.3s）
- 三種類のゴミを除去：ページ UI の語、メール/URL 行、**直近 30 条の字幕と 8 文字以上の共通部分文字列を持つ行**（自己循環の防止）
- 三種類の候補だけを抽出：4 桁以上の数字、4~10 拍のカタカナ、3~8 文字の漢字列。それぞれの読みを取得し（pyopenjtalk `run_frontend`、3ms/文）、読みが 4~14 拍にないものは捨てる
- 翻訳前に本文を形態素に分割し、1~4 形態素の読み窓を候補語の読みと編集距離で比較：**≤1 かつ表記が異なる**場合のみヒットとし、1 区間につき最大 1 語を提示
- ヒットしたときだけリクエストボディの末尾に `【屏幕词】「畔蒜泰助」——本句的「阪井泰介」若指同一事物，请改用屏幕写法。` を追加（37 文字 ≈ 25 token、約 +100ms、**その区間でだけ払う**）。ヒットしなければ token を一つも追加しない → コストゼロ、汚染ゼロ

**なぜラテン文字を扱わないのか**：OpenJTalk は `CloudflareObservability` を一文字ずつ 50 拍の「しーえるおー…」と読むので、日本語の読みとは永遠に一致しません。実測で 40 条の候補はすべてメール/URL の断片でした。画面の英単語は ASR も正しく書けていればそもそも提示不要で、カタカナに聞き取られた場合は **ASR のホットワード**で扱うべきで、この道ではありません。

#### 現状と検証方法
- unit を止めているとき `/api/status` の `screen` は `null`。有効時は `polls/hits/terms/sample/last_ms/last_hint` を返す
- ページのタイトルバーに「屏幕 N 词 · 命中 M」が増え、ホバーで語表のサンプル、直近のヒットと所要時間が見える —— **見えなければ効いていないのと同じ**なので、表に出している
- オンライン実測（`--screen-hints --screen-every 15`）：`q_tr=0`、`dropped=0`、lag≈290ms、初回 p50 は 473→443ms（ノイズ内、**測定可能なコストはなし**）。`terms` は 14~40 条で画面に応じて変化
- **実際のヒットはまだ一度も出ていない**：この期間の画面は Outlook のメール一覧、Web ページ、チャットウィンドウで会議内容と無関係だったため、`hits` はずっと 0。ロジックは `test_screen_hints`（15 組、読み器のスタブを含む）でカバー

#### 手で一度ヒットを作り、経路が本当に効くことを確認（35B 実測）
現網の実際の酷い文を一つ取り、人為的に画面語を与える：
```
原文（ASR）：同小委部同じベットネって違う夢見ているのか、見ないといけない。
ヒントなし → 同小委部是否抱着同样的期待，还是必须去确认？          ttft 299ms / pn=33
ヒントあり → 同小委员会是否做着不同的梦，必须加以确认。            ttft 364ms / pn=62
ヒント内容： 【屏幕词】「小委員会」——本句的「同小委部」若指同一事物，请改用屏幕写法。
```
**+29 token ⇒ +65ms** で、固有名詞は確かに直りました。機構は成立しており、欠けているのは「画面にその語が本当に現れること」だけです。

> 判定：この道の**上限は「固有名詞の同音誤字」**で、一般語の聞き間違い（`つぶさに` → `つぶさんに` のような救いようのないもの）は救えません。日常の会議では誤字の 90% が後者なので、全体の品質を押し上げることは期待しないでください。

### 4.26 ページが「接続中…」で止まり、ボタンがすべて無効：PAGE が raw 文字列でなく JS が壊れた（2026-11-21 午後）

現象（4.25 のリリース後、最初のリロード時）：ページには header と「音声を待機…」だけがあり、`已识别 0 段`、`延迟 —`、`-99 dB`、`连接中…`、三つのボタンを押しても反応なし。**しかもサーバー側は完全に正常** —— `systemctl is-active` は active、`/api/status` は 77 区間、`level_db=-29`、`/api/poll` は 30KB の JSON を直接返す。

#### 特定
スクリーンショットの四組の値は、まさに **PAGE に書き込まれた初期 DOM**（`<span id="db">-99 dB</span>`、`<span id="live">连接中…</span>`）でした。`paint(true)`（スクリプト末尾にあり、状態ランプを「実行中」に変える）すら実行されていない以上、「ネットワーク断 / SSE 接続不可」ではなく、**`<script>` 全体が走っていない**ということです。サーバーが返すページを取り出して node に渡します：

```
node --check /tmp/page.js
SyntaxError: Invalid or unexpected token   ← line 270
```

犯人は 4.25 で追加した tooltip：
```python
sc.title = ... + '\n错误：' + ...      # ソース上は問題なく見える
```
`PAGE` は当時ふつうの `"""` 文字列だったため、Python が `'\n'` を先に**本物の改行**として解釈し、ブラウザが受け取った JS はこうなっていました
```js
sc.title = (... + '
错误：' + ...)
```
単一引用符の文字列が改行で途切れる → スクリプトの構文エラー → 一文字も実行されない。**HTML は静的だから画面は「正常」に見え、スクリプトだけが死んでいた**のです。

#### 修法（二層）
1. `PAGE = r"""..."""` に変更して raw 文字列にする。JS 内の `\n`/`\u0001` がそのままブラウザへ届く（`voice_server.py` の `HTML = r"""` は元から raw だったので、こちらでは一度も踏んでいない）
2. `test_page_js_syntax`：レンダリング後の `<script>` を抽出して `node --check` に通し、さらに「単一引用符は各行で対になっていること」を確認するチェックを追加（node のないマシンではスキップ）

#### 教訓
- サーバーが healthy ≠ ページが生きている。**「ページが本当に JS を走らせたか」は、JS しか書き換えない初期値**（状態ランプ、dB、区間数）で判断し、サーバーログだけを見ない。
- `PAGE` に JS のエスケープを書くときは、まず raw かどうかを確認する。変更後は必ず `node --check` を通し、リロードして初めて気づくのを待たない。
- フロントエンドの変更は依然として**手動の F5** が必要（`PAGE` は定数で、サーバーの再起動はブラウザを更新してくれない）。

## 7. やること

1. **割り込み（barge-in）** —— ✅ 読み上げ中の発話で即停止（4.6 参照）、回り込みでは誤発火しない
2. **常時リスニング** —— ✅ ウェイクワード「小八你好」を接続済み（4.5 参照）、一ターン終了後は自動で待機へ戻る
3. **vLLM の自動起動（ブート時）** —— 現在は**ロールバック用の控え**でしかない（両サービスとも Magnitude の 35B を使う）、起動時に立ち上がらず、ロールバックするにはまず `docker start vllm-qwen`。サーバーは毎ターン死活確認するので順序は正しさに影響しないが、その間は先にエコー（オウム返し）へ降格する
4. **初回チャンク遅延の最適化** —— 636ms のかなりの部分が pyopenjtalk の音素化なので、初回文を短く切ることを検討できる
5. **単体テストの補完** —— `test_tts_routing.py` は声質ルーティングと文分割をカバー済み、`voice_server.py` の Silero 終了判定はまだ未対応未対応
6. **割り込みの実人声での校正** —— 現在は合成音で判定チェーンを検証しており、実人の話速/音量でのしきい値は実際の記録で一巡調整する必要がある
7. **キャプチャカードの業務復帰** —— ✅ 1080p30 の経路は開通（4.7 参照）、✅ フレーム抽出 → OCR → 会話への接続も完了（4.8 参照）；次は分区 OCR（ウィンドウ本体だけを認識）で 6 秒を 3 秒以内へ
8. **長時間キャプチャの給電検証** —— 現在はドック経由（166s で落ちたことがある）、時間単位の連続キャプチャの前に本体ポートへの直挿しを推奨
9. **4B–9B のスイートスポット** —— ✅ 実測でクローズ：62s の実音声で 9B は初回/全文とも負け（326/1085 対 35B の 293/693）で、しかも復読する。以前の 157ms は短文が与えたもの（4.21 参照）
10. **手で起動した dockerd を systemd へ引き渡す** —— 約 3 分の窓が必要（dockerd 停止 → コンテナ停止 → magnitude 冷起動 150s、両サービスとも断）。現在は失敗再起動のループを stop 済みで、次回のマシン再起動で自然に引き継がれるのを待つ（4.19 の警告参照）
11. **音声アシスタントの初回トークンをさらに下げる** —— 35B に替えて初回は 343~627ms で、7B より 170~370ms 遅い。試せるのは：`history[-6:]` を `[-4:]` に削る（新規 token が減る）、または 35B に短い system を使う（MoE では否定済み、4.20 参照。ただし音声シナリオで再測定が必要）
