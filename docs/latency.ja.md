# レイテンシ: 予算、測り方、どこがハードフロアか

[English](latency.md) · [中文](latency.zh.md) · [**日本語**](latency.ja.md)

このシステムにチューニングの余地はあまりありません。**時間の大半が物理に費やされる**からです: ASR は発話を最後まで聞き終える必要があり、MoE は prefill を行い、GPU は OCR を実行します。この文書では「削れるもの」と「追うのをやめるもの」を分けて説明します。

## 字幕 1 本のレイテンシ予算（本番実測）

```
発話終了
  ├─ 断句の締め（段階的ポーズ / soft-cut）        0.30~0.90s   ← 話すリズムで決まる。無駄ではない
  ├─ SenseVoice ASR                              ~290ms
  ├─ LLM prefill → 首字                          400~470ms   ← ttft_ms
  ├─ ストリーミング訳を 1 字ずつ送出                ~80ms/増分
  └─ 文全体の翻訳完了                             ~1000ms      ← trans_ms

感知レイテンシ lag_ms ≈ 290ms（音声から最初の 1 行が出るまで）
```

**要点**: 首字が届いた時点で表示を始めるので、ユーザーは `trans_ms` を待ちません。だからこそ `--no-stream-trans` は絶対に有効にしてはいけません —— 文全体が訳し終わってから表示すると、感知レイテンシは 0.26s から 0.8~1.3s に押し上がります。

## 首字の経験式（35B-A3B）

```
TTFT ≈ 65ms + 3.5~6.5ms × 新規 token        オンライン実測の傾き 4.5ms/token
```

「新規 token」とは、エンジンが返す `prompt_n`（**そのラウンドで実際に処理した token**）のことで、`prompt_n - cache_n` ではありません。`cache_n` は再利用分であり、両者を足したものがプロンプト全体です。**首字 200ms はハードフロア**です。それ以下を追わないでください。

ここから、直感に反する 3 つの結論が出ます:

| やること | 結果 | 理由 |
|---|---|---|
| system を 250 token から 70 に削る | **遅くなる** | ユーザー内容が毎文変わるため、短いプレフィックスは `cache_n` が常に 0（24/24）になり、全体の prefill を払い直す |
| `--ctx-lines 2 → 1` | **約 90ms 節約** | 上文の部分は毎文変わるので、本当に新規 token である |
| `--tr-workers 2 → 1` | 差なし | 単文のレイテンシは並列数に左右されない。VRAM の取り合いが減るだけ |

**長いプレフィックスはタダです**: 安定した長い system はキャッシュから再利用されます（約 290 token）。削るとかえって再利用を壊します。

## 7B vs 35B（同じ 62 秒の音声、長文での直接比較）

| | 7B-AWQ（dense、vLLM） | 35B-A3B（MoE、Magnitude） |
|---|---|---|
| 短文の首字 | **90ms** | 300~470ms |
| 長い回答の全文 | 遅い | **25~35% 高速** |
| 日中混在 / ハルシネーション | 誤る | クリーン |

MoE は 1 token あたり約 3B しか活性化しないのでデコードは安く済みますが、prefill ではほぼすべてのエキスパートを読むため高くつきます。**短い回答は dense が勝ち、長い回答は MoE が勝つ** —— 7B の直感を 35B に当てはめないでください。

## 判断基準（この 3 つの数値だけを見る）

```bash
curl -s localhost:8096/api/status
```

| フィールド | 健全 | 異常時にまずやること |
|---|---|---|
| `q_asr` | 0 | 増加 → ASR スレッド不足 / 収音が占有されている |
| `q_tr` | 0 | **増加 = 翻訳が追いついていない**: まず `--ctx-lines 1`、次に LLM が VRAM を奪い合っていないか確認 |
| `dropped` | 0 | >0 → キューがセグメントを捨て始めた。レイテンシはすでにリアルタイムを超えており、必ず対処が必要 |

`NRestarts` と `ActiveEnterTimestamp` を併せて見ると、無限再起動ループに陥っていないか判断できます。

## 自分のマシンで測る方法

```bash
.venv/bin/python tools/ttft_prompt_ab.py     # prompt のバリエーション × プレフィックスキャッシュ
.venv/bin/python tools/ttft_scenarios.py     # 文の長さ / 上文行数ごとの首字
.venv/bin/python tools/trans_stream_probe.py # ストリーミング vs 文全体
.venv/bin/python tools/sse_verify.py 45      # SSE 中間状態の数と間隔
.venv/bin/python tools/e2e_latency.py        # エンドツーエンド
.venv/bin/python tools/wav_seg_ab.py --wav x.wav --a 0.45 --b 0.7
```

## バグとして追わないもの

| 現象 | 真相 |
|---|---|
| 画面 1 回の読み取りに 3.4~3.9s かかる | キャプチャカードが 40 フレーム（約 1.2s）を捨てる + OCR ≈ 行数 × 30ms |
| ページのフロントエンドを変えても反映されない | `PAGE` は定数: サービス再起動 + **ユーザーによる F5** |
| `cache_n` がずっと 0 | ユーザー内容が毎文変わり、プレフィックスが無効になる。キャッシュが壊れているわけではない |
| vLLM が 35B のプレフィックスキャッシュにヒットしない | 1056 token 粒度という、モデル + エンジンの物理的特性 |
| 首字を 200ms 以内に抑えられない | 65ms の固定オーバーヘッド + prefill。ハードフロアである |
